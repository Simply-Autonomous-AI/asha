asha Documentation / asha CLI Reference

Command line interface

./asha is the one command: it posts messages, launches and watches agents, and manages the daemon.

verified 2026-09-29asha 0.1.1Node ≥ 22code: src/cli/commands.ts

In short

  • Build once with npm install && npm run build; ./asha never runs npm.
  • Results go to stdout. stderr carries only what you must see — ✗ errors, ⚠ warnings, and the one › line saying which user ID your login name was sent as, when it had to be converted — unless you add --verbose, which adds the › progress lines and the models' output as they generate it.
  • --interactive keeps a session open: type a message per line, /watch on for the whole channel, /quit or Ctrl-D to leave.
  • Exit 0 success, 1 failure, 2 malformed command line, 130 Ctrl-C in an interactive session.
  • The daemon starts itself when needed and runs until asha --stop (./asha --stop in a checkout); stop it after a rebuild or brew upgrade asha.
  • Walkthrough with real output: the guide; past corrections: history.

Build time and run time

StageCommandWhat happens
Build timenpm install && npm run buildAfter any source change; build is rm -rf dist && tsc -p tsconfig.build.json (package.json).
Run time./asha …The asha script follows symlinks and runs exec node dist/src/cli/main.js "$@". Unbuilt, it prints asha: not built — run `npm install && npm run build` in <repo> first to stderr and exits 1.
  • main.ts injects the CliContext (streams, fetch, spawning, signals, bounds) into runCli in commands.ts, which returns the exit code.
  • The build fingerprint: 12 hex digits of a sha256 over every .js file under dist/ (buildFingerprint in src/shared/build.ts).
  • Symlink the script onto your PATH to run it anywhere; it uses the first node there.

asha — Autonomous Simple Harness for Agents

usage:

       [file=<path> ...] [posts=<n>] [tokens=<n>] message=<text>
                   post a message to a channel (default "main"), first
                   bringing the recipe's agent online there if one is named;
                   to= sends it to one agent (e.g. to=hewo-1) instead of
                   everyone, topic= to the agents of a team that subscribe
                   to that topic. posts= and tokens= are its conversation's
                   budget: the agents' messages in it (1 to 32; 32 without
                   it) and their model calls' tokens (1 to 1,000,000; none
                   without it), past which it ends. user= says who you are
                   (e.g. user=alice);
                   without it you are your login name on this Mac, made to
                   fit a user ID (John.Smith is sent as john-smith, and
                   says so). file= attaches a file (repeat it for more, at
                   most 10): every agent on the channel can read it. Prints
                   the replies meant for you, saves the files an agent
                   returns as ./asha-files/<channel>/<name>, and returns
                   once no agent is still working on it

                   answer what an agent asked you: the line "? <handle> is
                   waiting for your answer" gives this command, its
                   conversation= filled in

                   replies. A word in a line that is a file's path (it has a

                   leaves; Ctrl-C leaves at once (exit 130), abandoning the
                   reply to a message still being worked on

                   start a new agent for the recipe on a channel (another
                   one, if one is already there) and print its handle

                   start every member of teams/<team>/ on a channel, each
                   under its own name, and print their handles, one a line
  asha --watch [channel=<channel>]
                   print every message on the channel as it happens, until
                   Ctrl-C

                   open the portal, asha's web page, in your browser: every
                   command here, a live picture of a channel's agents, and
                   their telemetry; user= says who you are there

  asha --status    report whether the daemon is running, and its agents
  asha --stop      stop the daemon and every agent it runs
  asha --stop channel=<channel>
                   stop one channel's agents, then every model server no
                   agent still needs; the daemon keeps running
  asha --list-state
                   list what persisted agents and teams have saved: one line
                   per saved asset and per agent's unsaved messages, then the
                   total

                   remove saved state: everything, a channel's agents and
                   board, or one agent (team= for a team member); all and
                   channel= list what goes and ask you to type reset (--yes
                   when not at a terminal)
  asha --reset-state channel=<channel> [name=<name> [team=<team>]] user=<id> [--yes]
                   erase one user's saved memory from the agents named; files
                   and boards are shared by every user and are kept
  asha --install-module path=<dir> [archive=<file>] [--yes]
                   install a module from a directory (from this repository's
                   modules/, or a separate package): its files, licences and

asha prints only each command's output on stdout; errors (✗) and warnings (⚠)
always go to stderr. The daemon starts on its own when a message,
--interactive, --launch or --watch needs it.

How arguments are read

runCli strips --verbose wherever it appears and refuses --quiet wherever it appears (below); --interactive anywhere starts a session with the rest (parseInteractiveArgs); then a first --launch or --watch takes the rest; --server, --status, --stop or --help runs only alone; anything else is a message (parseConversationArgs).

Arguments are key=value (parseKeyValues): known keys, once each, non-empty, split at the first =. Quote spaces: message="Please say: Hello World.".

A malformed line prints the reason and usage to stderr and exits 2, contacting no daemon (run 2026-09-27):

./asha message=a message=bmessage= given twice
./asha bogus=1 message=xunrecognized argument: bogus=1
./asha --help extraunrecognized argument: --help
./asha --launch or ./asha --launch channel=x--launch takes recipe=<recipe> and optionally channel=<name>
./asha --watch foo=1--watch takes only channel=<name>
./asha --quiet message=x (anywhere)--quiet is gone: asha is quiet by default; add --verbose for progress
./asha --interactive message=x--interactive takes no message=: type each message after it starts
./asha --interactive file=a.txt✗ file= is for a single message: in --interactive, a path in a line attaches its file
./asha --interactive --watch (or --launch, --status, --stop, --server, --help)--interactive cannot be combined with --watch

The daemon checks values: a channel matches ^[a-z][a-z0-9-]{0,31}$ (NAME_PATTERN in protocol.ts); a typed user= is user-<n> or such a name, not ending -<number>, not asha — the user-ID rule, userIdProblem in protocol.ts, which claimUser in src/daemon/channel/index.ts applies. The CLI does not check a typed user=: ✗ the daemon rejected the message: HTTP 400: {"error":"\"Bob\" cannot be a user ID: a user ID is 1 to 32 characters: a lowercase letter, then lowercase letters, digits or hyphens"} (the daemon's JSON body, as printed), exit 1.

Your login name is as unverified as a typed name (D2): anyone who runs asha can say they are anyone. Files: attaching, and the files an agent returns

(docs/plans/agent-files.md R1–R3a, R7, R8, R12a, R13; the daemon's side is the channel file space.)

Every channel has a file space, /channel in each of its agents' containers. A file you attach is copied into it, and every agent on the channel can read it, and so can every user's agents after you — a channel's files are shared by everyone on it, as its board is. The agents see the file at /channel/upload-<16 hex>/<name>: each upload gets a folder of its own, so a second file of the same name never replaces the first, and two files of one name in one message land as <name> and <name>-2 (a dot keeps its suffix: a.tar-2.gz). The message tells each agent, one line per file after its text: Attached file: /channel/upload-…/notes.txt (120 bytes).

Attaching. file=<path> on a single message (--interactive attaches by a path in a line instead). The CLI reads each file itself — the daemon never opens a path you name — through one open descriptor, after these checks, any failure printed ✗ <path>: <rule> with exit 1 and nothing sent (readAttachment in src/cli/attach.ts):

The credential deny list (CREDENTIAL_DENY_LIST in src/shared/credentials.ts) is compared on the path with every symbolic link resolved, after Unicode NFC and lower-casing (the Mac's disk ignores case): any path component .aws, .ssh, .gnupg, .docker, .kube, .azure, .terraform.d, .password-store or .claude; anything under .config/gcloud, .config/gh, Library/Keychains, Library/Cookies, Library/Safari, or the Chrome, Firefox and Microsoft Edge folders of Library/Application Support; a file named credentials, credentials.*, .git-credentials, .netrc, .npmrc, .pypirc, .pgpass, .vault-token, .env, .env.*, an SSH key (id_rsa, id_ed25519, … and their .pub), *.pem, *.key, *.p12, *.pfx or *.kdbx; and anything under ASHA_HOME. It matches names and paths only: a secret written inside any other file is sent like any other text — except asha's own two secrets, which the daemon refuses in any upload (below). (Amended 2026-10-02 by docs/plans/portal.md R8b, from the owner's answer to its question 6: this said names only, with no exception.)

What is sent. First POST /v1/channel/space makes sure the channel's file space exists (with recipe=, readying the recipe's image; the agent comes online with the message) and reports what the space holds and which agents on it are cloud-granted; then the files go up in one streamed upload (POST /v1/channel/files, a manifest line naming each file's name, size and sha256, then the bytes — the CLI never holds a whole file in memory); then the message is posted naming the upload. The path you typed reaches the agents: the file's name is in the line they read, and an interactive line is posted as typed, so /Users/you/Clients/acme/plan.pdf what is this? tells them that folder's name. The upload is refused whole when the daemon finds a file's bytes differ from what the CLI measured (it changed while being sent): ✗ upload to channel <channel>: 400 sha256_mismatch …, and nothing of it stays in the space. It is refused whole too when a file holds asha's own control credential or model-server key, the daemon searching each file's bytes as they pass (a copy of daemon.json made outside ASHA_HOME, say): ✗ upload to channel lab: 400 holds_asha_secret: daemon-copy.json holds asha's control credential, exit 1, no byte of the value copied, nothing logged that names it (the upload route; the portal uploads the same way). That check does not catch: any other program's secret; asha's values in another form (upper case, base64, split by a line break, compressed, or inside an archive); the dead credential and model-server key of an earlier daemon run (a crash leaves its model-server.key behind); agent tokens; a value typed into a message's text or a file's name; a value split across two files. Other refusals, each ✗ upload to channel <channel>: <status> <reason>: <detail>, exit 1: space_entries, space_bytes (413), too_many_uploads (429: a channel holds at most 100 uploads not yet named by a message), space_busy (503: another upload held the space for 60 s), copy_failed, copy_timeout, rollback_failed. An upload answers within 260 s or fails ✗ upload to channel <channel>: no answer in 260 s.

Seeing what was attached. With --verbose, one line per file on stderr: attached ./notes.txt as /channel/upload-3f9c…/notes.txt (120 bytes). Without it nothing is printed — so a sentence can attach a file you meant only to mention (in an interactive line, a word with a / that names an existing file attaches it). Run with --verbose to see, or read the daemon log's files.attached record, one per file: your user ID, the channel, the agents it reached, and the file's name, size and sha256 — never the path on your Mac or the bytes.

A cloud-granted agent. When an agent on the channel, or the recipe being launched, is granted a cloud service, the CLI prints ⚠ <agent> is cloud-granted: files on channel <channel> may leave this machine before anything is uploaded — always, with or without --verbose. A launch of a cloud-granted agent onto a channel whose space already holds files prints the same line. A recipe is cloud-granted when it grants a module that lists a host, or names a hosted model (what leaves the machine). Every agent on the channel, cloud-granted ones included, receives the user field of each message — by default your login name, converted to fit the user-ID rule — so it can reach a cloud module's vendor (the owner's answer, user-to-cloud, 2026-09-27).

Files an agent returns. An agent whose recipe selects reply_with_files can answer with files from /channel (the tool). The CLI saves each one as ./asha-files/<channel>/<name> under the folder asha runs in, and prints on stdout, after the reply's text:

file: asha-files/lab/summary.txt (812 bytes, sha256 9b1e…)

It never overwrites: a name already taken — by a file, a folder or a symbolic link — saves as <name>-2, -3, …, and a link at the name is never followed. The bytes go to a partial file .asha-partial-<16 hex>, made new, then checked against the reply's size and sha256 and given its name; a download that ends short, does not match, or stalls 30 s prints ✗ file <name>: <rule>, exit 1, and leaves no partial. The folder asha-files (and the channel's folder in it) must be a real folder: a symbolic link there is refused. A saved file is mode 0644. --watch and other users never fetch: they see the file's name, size and sha256 only.

Binary files attach and return like any other, byte for byte; an agent's read_file answers not_text for one, so a model reads text files only. Erasing a user (--reset-state … user=) keeps the files they attached and a persisted channel's file table: files are shared by everyone on the channel.

The models' output, as it is generated

With --verbose the models' output is printed on stderr as it is generated (DeltaPrinter in commands.ts; since 2026-09-29, docs/plans/model-streaming.md). For a forced tool call, which is every agent turn, the fragments are the raw JSON of the call's arguments — for reply, its text inside JSON quotes and escapes — while stdout gets the reply itself, whole, as without --verbose. A delta line is ended before any other line is printed. The deltas include what no message carries: a model's thinking (for a recipe that turns it on, thinking), and drafts the agent's channel layer refused, such as a message to a handle that is not on the channel.

When no agent answers, the command still fails

Every case exits 1 (ConversationTracker in commands.ts):

  • Normally the harness posts an output from asha (HARNESS_HANDLE) saying what each agent did, or No agent on channel "<channel>" received this, so nobody could answer it., printed on stdout like a reply, with no ✗ line.
  • With no reply at all, not even the harness's: ✗ the conversation ended with no reply at all, not even the harness's: , then each agent that left (<handle> left the channel (<detail>); ), then a defect in the daemon; see its log, or the daemon runs a different build than this asha (see asha --status) when it does.

Exit 0 when an agent replied; 1 on the no-answer reply, an error event, a non-2xx answer (✗ the daemon rejected the message: HTTP <status>: <body>), early close (✗ the daemon closed the conversation before it settled; see its log, followed by the socket's reason in parentheses when the daemon stopped mid-stream), 60 s of silence (✗ no word from the daemon for 60000 ms; see its log), or no daemon; 2 malformed.

--launch built

./asha --launch recipe=<recipe> [channel=<channel>] [--verbose]
./asha --launch team=<team> [channel=<channel>] [--verbose]

launch sends POST /v1/agents with {recipe, channel} or {team, channel} (default main), streaming LaunchEvents. A recipe: to launched or error; it always starts a new agent (hewo-1, then hewo-2). Progress, with --verbose: › image: asha-image-hello-world current, › hewo-2: Hi. A team (teams/<team>/, team): every member in team.json's order, each under its own name, printing each handle on stdout as it comes online, to team_launched or error. Progress per member, with --verbose: › member supervisor (recipe supervisor), then its phases and its Hi. Every member's recipe and documents are checked before any container starts, and a member that fails to come online stops the members already started; the error names the member and why, for example ✗ internal: team crew: member "helper" did not start: …/helper.json: document "gone.md" does not exist in the recipe's folder.

Exit 0 launched (every member, for a team); 1 on an error event, a non-2xx answer (✗ the daemon refused the launch: HTTP …), early close before launched (or team_launched), 60 s of silence, or no daemon; 2 without exactly one of recipe= and team=, or with extras.

example, from the guide

--interactive built

./asha --interactive [user=<id>] [recipe=<recipe>] [channel=<channel>] [to=<handle>] [--verbose]

A session on one channel (default main): each line you type, ending with Return, is posted as one message, exactly as message=<line> would be, and its replies are printed; then the next line is read. interactive in src/cli/interactive.ts runs it, reusing converse for every message.

  • Lines. One message per line, so a pasted block of three lines is three messages. The line is text as typed: key=value inside it is text. A blank or all-whitespace line is skipped. Piped input works the same (printf 'a\nb\n' | ./asha --interactive user=bob); a last line without a newline is a message too.
  • A path in a line attaches its file (files; lineAttachments in src/cli/attach.ts). The line is split into words at spaces and tabs; a backslash makes the next character literal (my\ file.txt), and a word that starts with a quote and ends with the same quote is one word, the quotes removed ('my file.txt') — as a path dragged in from Finder is typed. Only a word that contains / or starts with ~/ is tried, so a file in the current folder is ./notes.txt: a bare notes.txt stays text and attaches nothing. Punctuation after or before a path is tried off it too (./notes.txt? attaches ./notes.txt). ~/ is your home folder. A word that names nothing, or a folder, stays text silently. A word that names a file that cannot be attached — the deny list, a hard link, over the bound, an eleventh file — stays text, prints ⚠ not attached <path>: <rule> always, and the message is sent without it. At most 10 files a line. The line is posted as typed, path and all. file= is refused for a session (✗ file= is for a single message: in --interactive, a path in a line attaches its file, exit 2).
  • Returned files are saved as for a single message, each file: line printed after its reply; with /watch on, after the view has printed the reply.
  • Every message carries the session's user=, to= (else everyone) and recipe=, so the first message brings the recipe's agent online and a later one brings it back after a daemon restart; nothing is launched before the first line. Each message finds or starts the daemon afresh from daemon.json, as a single command does.
  • One at a time. The next line is read once no agent is still working on the message before; lines typed meanwhile wait in the input and are handled in order. Each message keeps the single command's 60 s stream-silence bound; the prompt itself waits for as long as you like.
  • Failures don't end it. A message that fails prints its ✗ line and the session goes on; the exit code at the end is then 1.
  • The prompt asha> is printed on stderr before each line is read, only when input is a terminal. The terminal keeps its own line editing (Backspace, Ctrl-U); there is no history.
  • Who speaks. Every message comes from one user: the typed user=, or else your login name, converted and checked once before the first prompt exactly as for a single message — a changed name is announced once, a name that still breaks the rule ends the session before the prompt, exit 1. (Until 2026-09-29 a session without user= was refused, while the login-name default was not built.)

Commands — a line whose first word is / followed only by letters, and is not an existing file or directory (so a line starting /tmp or a dragged-in /Users/me/report.pdf is a message):

CommandDoes
/quitEnds the session once the lines before it are done; nothing after it is read.
/watch onSwitches stdout to the whole channel, printed as --watch prints it, with » reply from <handle>: before each reply to you; prints watching the channel on stderr. It returns once the daemon watches the channel, and a message is done only once the view has printed its replies — waiting at most 60 s (the stream-silence bound), after which a reply the view has not shown is printed from the conversation after ⚠ the channel view did not show this reply within 60000 ms; printed from the conversation:. The view keeps printing between messages, while the prompt waits. With --verbose, the view prints the models' output (deltas) and the conversation prints none, so each fragment appears once.
/watch offBack to only your replies; prints replies only.
anything elseunknown command /<word>; type /quit to leave on stderr; nothing posted; the session goes on and exits 1. /watch with any argument but on or off is one.

If the channel view's stream is cut (the daemon stops, or 60 s of silence), the session prints the ✗ line --watch would, turns the view off, counts a failure, and goes on; a reply to the message in flight that the view had not shown is printed from the conversation, so none is lost. It does not reconnect — type /watch on again.

If reading your input fails (the terminal went away), the session prints ✗ reading your input failed: <reason> and exits 1.

Leaving. /quit, or the end of input (Ctrl-D at the start of a line, or the end of piped input) once every line read is done: exit 0, or 1 if any message or command failed. Ctrl-C ends the session at once with exit 130: a message still being worked on is abandoned — the CLI hangs up its stream, the agents keep working, and their reply is lost. The terminal's mode is never changed, so nothing needs restoring. (--watch, by contrast, exits 0 on Ctrl-C, because that is how a watch ends.)

With --verbose, each message's progress is printed as for a single message, its posted line naming your user ID.

What saved state costs, and what a reset does not reach

  • Anyone who can run asha can read, reset or erase any user's saved state by naming them: saved memory, /workspace and a persisted board are served to whoever claims the user name or uses the channel (D2).
  • A full /memory (64 MiB, 4,096 files or 8,192 entries for the whole agent) stops being saved for every user of that agent, each later checkpoint failing over_bound (state.save_failed in the log each time; the ⚠ … not being saved line once per agent per daemon run), until a reset or an erase makes room.
  • Backups (Time Machine) made before a reset or erase still hold what it removed; so does the info-level channel.user_online log line.
  • An erase removes one user's own memory, not what others' memories say about them: another user's saved memory that mentions them is kept (agent-persistence R16). Corrected 2026-09-29 by the completion review: this limit was missing.

Control characters on a terminal. When stdout or stderr is a terminal, every C0 or C1 control character and DEL (U+0000–U+001F, U+007F–U+009F) except line feed and tab in what the CLI prints there is printed as � (U+FFFD), so a model's reply or another user's message cannot move the cursor, retitle the window or set the clipboard (OSC 52). Output to a pipe or a file is byte for byte (scrubControl in commands.ts).

Finding and starting the daemon

A message (and each message of a session), /watch on, --launch and --watch start one if needed; --status and --stop only look.

Finding (findDaemon, with parseDaemonFile):

  1. Read <home>/daemon.json (DaemonFile: {pid, port, credential}, and stopping: true while the daemon stops; mode 0600). No file: not running. A file saying stopping: true is a stopping daemon when its pid is alive and is an asha daemon — ps -o command= -p <pid> (2,000 ms bound) ends with /dist/src/cli/main.js --server — and not running otherwise (a crash or a reboot that left the file, its pid dead or reused); the health is not asked. A stopping that is not exactly true makes the file unreadable (below). A file that is not JSON, whose pid or port is missing or mistyped, or whose credential is present but not a non-empty printable string, fails every command, exit 1, never read as "not running": ✗ <home>/daemon.json cannot be read as a daemon file: <what is wrong>. If no asha daemon is running for this home, remove it.
  2. GET http://127.0.0.1:<port>/v1/health with Authorization: Bearer <credential>, within 3 s (a HealthResponse). The CLI sends the credential this way on every request it makes (the two APIs).
  3. A 401 from a port whose file names a dead pid means the daemon crashed and another server took its port: (daemon file names pid <pid>, which is not running; port <port> now belongs to another server), and the CLI goes on as if no daemon ran (a message starts one). A 401 with the pid alive means a daemon answers but the file is not its own. It fails, exit 1, and starts nothing (a second daemon would only meet the held lock): ✗ the daemon on port <port> refused the credential in <home>/daemon.json (HTTP 401), so that file is not this daemon's. If no asha daemon is running for this home, remove the file.
  4. No answer prints (daemon file names port <port>, which did not answer: <error>), once per command however often a start polls the file (notedStalePorts); that or another non-2xx counts as not running — but a 503 with reason: 'stopping' from a live asha daemon (checked as in 1) is a stopping daemon: one that began to stop before it rewrote its file.
  5. A different build prints the ⚠ warning, with or without --verbose, once per build in a command or an interactive session; a daemon too old to say shows unknown, from before builds were tracked.

A stopping daemon (since 2026-10-03, docs/plans/debt-paydown.md R16; D21, now paid): --status prints stopping (pid <pid>), exit 1; --stop sends nothing and waits (--stop); every other command prints ⚠ the asha daemon (pid <pid>) is stopping; waiting for it to stop on stderr, with or without --verbose, polls its pid every 200 ms up to 90 s (the daemon's slowest clean stop, SERVER_STOP_MS), then goes on as if no daemon ran — a command that starts one starts one; past 90 s: ✗ the asha daemon (pid <pid>) was still stopping after 90000 ms; see <home>/logs/daemon.jsonl, and if no asha daemon runs for this home, remove <home>/daemon.json, exit 1 (findDaemonAfterStop in commands.ts). A start's own poll treats a stopping daemon as not yet up. Before this, a stopping daemon read as absent: --status said not running, and a message started a second daemon, which then met the held lock. An older CLI meeting a newer daemon ignores stopping and reads the 503 as absent, as before.

A daemon from before credentials wrote {pid, port} with no credential. Its health is asked without one; if it answers, every command but --stop fails, exit 1: ✗ the running daemon (pid <pid>, port <port>) predates credentials: it serves its API to any local process. Run asha --stop to replace it with this build. --stop stops it as before (SIGTERM, then stopped (pid …)).

Starting (startServer, spawnServer):

  1. Spawn node dist/src/cli/main.js --server, detached, stdin ignored, output to <home>/logs/server.log.
  2. With --verbose, print › started the asha daemon (pid <pid>); log: <home>/logs/server.log (the owner's answer of 2026-09-27: announced only with --verbose).
  3. Look every 200 ms, up to 20 s.
  4. If it dies, look once more (another CLI may have won); otherwise ✗ the daemon exited during startup; see <server.log>, exit 1.
  5. After 20 s: ✗ the daemon did not answer within 20000 ms; see <server.log>, exit 1.
