asha CLI guide

asha runs AI agents in local containers that talk on named channels and use open-weight models on your machine. This guide shows real output: one agent saying hello, then one agent asking another.

captured 2026-09-26 and 2026-09-29verified 2026-09-29Apple M4 Pro · macOS 26.5.2asha 0.1.0 (2026-09-26), 0.1.1 (2026-09-29)model Qwen3-8B Q4_K_Mcolima 0.10.1llama.cpp build 8130

In short

  • Build once (npm install && npm run build), then run ./asha; it installs colima, Docker and llama.cpp itself.
  • The first message takes about 78 s (the 5 GB model download); after that, replies take under a second.
  • Use to= to address one agent and --watch in a second terminal to see agents hand work to each other.
  • asha prints only the reply (stdout); on stderr only ✗ errors, ⚠ warnings and the line naming the user ID your login name was sent as, when it had to be converted (CLI reference); add --verbose to see the progress lines these transcripts show. Failures exit non-zero either way.
  • --interactive keeps a session open: one message per line, /watch on for the whole channel, /quit to leave.
  • Every flag in detail: the CLI reference. Past corrections: history.

The left gutter names each line's source:

The last line of each is the exit code and time. Output is copied from real runs, except that the scratch home is shown as the default, ~/.simplyautonomous/harness, and the login name as you.

Install

From a checkout, you need Homebrew and Node.js ^22.13.0 || ^24.0.0 || >=26.0.0 (engines.node in package.json). Build once, and again after changing the source; run time never runs npm, and installs colima, the Docker CLI and llama.cpp through Homebrew when first needed.

build time · fresh clone0.9 s
$ npm install && npm run build
added 40 packages in 338ms
> simplyautonomous-ai-harness@0.1.0 build
> rm -rf dist && tsc -p tsconfig.build.json
[exit 0, 0.9 s]

Before a build, ./asha says asha: not built — run `npm install && npm run build` in … first. To run it from anywhere:

$ ln -s "$PWD/asha" /usr/local/bin/asha    # optional; the script follows the link back to the repo

Or: run a release

A release is the tarball npm run release makes of one tagged commit and its build (Deployments); unpacked, its ./asha runs as a checkout's does, with no build. No tap for Homebrew is published, so this guide gives no brew command (docs/plans/oss-release.md R31).

Two agents: one asks the other

On its own channel, duo, apart from main.

  1. Start two agents

    --launch always starts a new agent and prints its handle; the second is hewo-2.

  2. Ask hewo-1 to have hewo-2 say it

    both agents running · recaptured 2026-09-29 at aa036195.8 s
    $ ./asha --verbose to=hewo-1 channel=duo message="Please ask hewo-2 to say Hello World."
› you → hewo-1 on duo: Please ask hewo-2 to say Hello World.
› hewo-1 send_message: {"to": "hewo-2", "text": "Say: Hello World"}
› hewo-1: ok
› internal hewo-1 → hewo-2: Say: Hello World
› hewo-2 reply: {"text": "Hello World"}
› hewo-2: ok
› output hewo-2 → you:
Hello World
[exit 0, 5.8 s]
    1. Your message went to hewo-1 alone, as you (your login name).
    2. hewo-1's model chose send_message — the › line with the tool's name is its output as it was generated (deltas) — then it said ok and posted the internal "Say: Hello World" to hewo-2.
    3. hewo-2's model answered with reply, and the reply reached you; with no agent still working, the command returned.

    Both run the same image and recipe, and must answer every message with one of four tools:

    • reply(text): the only way words reach you.
    • send_message(to, text), to being all-agents or a handle; not given to an agent alone on its channel.
    • list_agents(): who is online and what each does, from recipe descriptions. Ask for "the agent that translates" and it calls list_agents first.
    • pass(reason): no action.

Just the answer

A command prints only the reply on stdout (with --launch, only the handle), so reply=$(./asha …) captures just the answer; the few lines on stderr (✗, ⚠, and the login-name line) never mix into it. A failure still prints its ✗ line and exits non-zero. (Until 2026-09-28 this took --quiet, which is now refused, exit 2: CLI reference.)

hewo-1 already online · captured 2026-09-291.3 s
$ ./asha message="Please say: Hello World."
Hello World.
[exit 0, 0.7 s]
$ reply=$(./asha message="Please say: Hello World."); echo "hewo-1 said: $reply"
hewo-1 said: Hello World.
[exit 0, 0.6 s]

Interactive: a session

--interactive reads one message per line until /quit or Ctrl-D, and prints each reply as it comes; /watch on shows the whole channel instead, /watch off only your replies again. Without user= it speaks as your login name, as a single message does (CLI reference). The prompt asha> appears only at a terminal; piped, the session prints the replies on stdout, and on stderr only ✗ and ⚠ lines, watching the channel or replies only for those commands, unknown commands, and the line naming the user ID your login name was sent as, when it had to be converted. A command it does not know is reported and counted as a failure:

The first reply is printed as in a single command; after /watch on, stdout is the channel view, with the mark before the reply to you. With --verbose, each message's progress is printed as for a single command.

Stopping and restarting

stops the daemon, its agents and its model server · captured 2026-09-291.4 s
$ ./asha --stop
stopped (pid 80580)
[exit 0, 1.3 s]
$ ./asha --status
not running
[exit 1, 0.1 s]

--stop returns once the daemon has removed every agent container and stopped llama-server; colima keeps running. The model and image stay cached, so the next message restarts in seconds.

You need not stop it yourself (since 2026-10-15, its lifetime): a daemon a command started for you stops itself after 30 minutes with no agent and nothing open — an open --watch or portal tab keeps it — and a model nobody has used for 15 minutes is unloaded, freeing its memory, and loaded again by the next message that needs it. To keep a daemon however idle, start it yourself with ./asha --server; ASHA_IDLE_EXIT_MS and ASHA_MODEL_IDLE_MS change the two bounds (environment). A daemon that dies takes its llama-servers with it. Your login name is the same after a restart, so agents that remember users by ID know you again; issued user-<n> IDs (control-API clients only) are never reused, even after a restart.

[exit 1, 0.1 s]

missing message=
   … usage follows …

Exit 0 is success, 1 a failure (including running before a build), 2 a malformed command line. A failure line is ✗, a reason from a fixed set, and details. Every failure the daemon has seen:

$ jq -c 'select(.level=="error")' ~/.simplyautonomous/harness/logs/daemon.jsonl

Reference

Every command and option (./asha message=<text> with user=<id> (a name such as alice, or an issued user-<n>; without it, your login name), recipe=<r>, channel=<c>, to=<handle>; ./asha --launch recipe=<r> [channel=<c>], ./asha --watch [channel=<c>], ./asha --interactive [user=<id>] [recipe=<r>] [channel=<c>] [to=<handle>], ./asha --status, ./asha --stop, ./asha --server, ./asha --help, --verbose) is in the CLI reference. ASHA_HOME (default ~/.simplyautonomous/harness) and ASHA_MODELS_DIR (default $ASHA_HOME/models) are under environment; the files under the home (daemon.json, mode 0600, which holds the daemon's pid, port and the control credential the CLI sends; model-server.key, mode 0600, the key llama-server requires; users.json, logs/daemon.jsonl, logs/server.log, logs/agents/<container>.log, logs/model-server-<model>.log, models/sha256-…/) under Deployments.

Everything runs on your desktop: the daemon listens only on 127.0.0.1 and models run on your GPU. Inside: Architecture; model pins: Models.
