# Portal user interface

`asha --portal` opens a web page in your browser that does everything the command line does to the daemon, shows the agents on a channel as a small robot crew — what each says, what it is working on, what it has collected — beside a chat of the channel you can post into, runs any pattern demo at a click, and shows each agent's telemetry. The daemon serves the page itself, on the `127.0.0.1` listener it already has: no new process, port or package.

> [!SUMMARY]
> - Run `asha --portal` (or `asha --portal user=<id>`): it starts the daemon if needed and opens the page in your default browser.
> - Send and Watch show their messages as chats — yours on the right, the agents' on the left, the harness's as notes — each with a **Command-line view** that prints exactly the lines its command prints, from the same code; Launch, Status (and Stop), State and Help print them always.
> - Watch draws the channel as robots saying what they say, with what each is working on and what it has collected above it, names the teams and recipes on the channel, lets you post a message, runs any pattern demo but P25 and P20 with **Run demo**, and ends its agents with **Stop demo**.
> - Recipes and teams are picked from drop-downs read from the daemon (`other…` takes any name).
> - A failure is shown where it happened and reported to the daemon's log as `portal.client_error`, never with your words, a user ID or the credential.
> - The page holds the daemon's credential in that browser tab only; it stops working when the daemon restarts — run `asha --portal` again.

## Opening it {#open}

```sh
./asha --portal              # as your login name, converted to a user ID as a message is
./asha --portal user=alice   # as alice
```

`--portal` finds the daemon, or starts it, exactly as a message does, and takes your user ID from `user=` or from your login name (`defaultUser`: a name that cannot be a user ID is refused, with its `✗` line, exit 1). It then writes `ASHA_HOME/portal.html` — a new `0600` file renamed into place, replacing any earlier one — whose only content is a script sending the browser to `http://127.0.0.1:<port>/#c=<credential>&u=<user ID>`, and runs macOS `open` on that file. It prints exactly

```text
portal: http://127.0.0.1:52311/
```

on stdout and exits `0` once `open` has. If `open` cannot be started, exits non-zero, or has not exited within 10 s (it is then killed), it prints `✗ could not open a browser (<reason>); open <file> in one` and exits `1`: open the named file yourself. Any other argument is a usage error (exit `2`). The credential appears in no output, in no process's arguments (`open` is given the file's path) and in no log record ([`portal` in `commands.ts`](../../src/cli/commands.ts)).

The page reads the credential and user ID from the address once, then removes them from it (`history.replaceState`): the address bar shows `http://127.0.0.1:<port>/`. It keeps the credential in memory and in the tab's `sessionStorage` only — a reload keeps it, closing the tab drops it ([`session.ts`](../../src/portal/session.ts)).

## The watch view's chat, and posting into it {#chat}

Each message on the channel is shown as a messaging app shows it ([`chat-thread.ts`](../../src/portal/chat-thread.ts)): a user's message as a bubble on the right, an agent's on the left — a message between agents dashed, a reply to a user green — each naming its sender, its addressee (`→ <handle>`, `→ <user>`, `→ topic <topic>` or `→ everyone`) and its time (`HH:MM:SSZ`, as the CLI prints it); a call's question labelled `asks` and an answer `answers`. An agent's greeting as it comes online — its status outside any conversation, `Hi` — is a bubble on the left too, `→ everyone` (*since 2026-10-08, the owner's request; until then a note*). So are two statuses the harness posts for an agent (*since 2026-10-16, the owner's requests; `docs/plans/demo-scene-refresh.md` R6, R7, R14*): `system failure — offline`, in red, when an agent online went offline with no stop asked of it — its container exited or its channel stream closed — before it is restarted or leaves; and a launcher's `launching a new <recipe> agent` as it starts one, then `could not launch a <recipe> agent: <reason>` if that fails. An agent its recipe restarts has its restart told the same way, in red while it is down (*since 2026-10-16, R16*): `restarting (1 of 2 within 60 s)`, `restart 1 failed: its container exited before coming online` for one that dies before it is back, `restart limit reached (2 within 60 s): removed` before it leaves, and, once back, `sent again the message it held`. None reaches any agent. Notes, centred: an agent's status in a conversation (`lead-1: ok`, `other-1: pass: busy`), an agent joining or leaving, the harness's notices and replies (`asha: …`), and a call's gather (`collected 2/2 answers`, then each agent's outcome). An agent's `consult refused: <reason>` is a warning in words — for `post_budget`, *lead-1 could not ask: this conversation has used up its posts budget (32 agent posts unless the message set Posts budget; each agent asked takes 2)*. While an agent's model is writing, the chat ends with `<agent> is writing…`. The chat follows the newest message unless you have scrolled up more than 40 px. **Show details** applies to the command-line view.

Under the chat, while you watch, a message box like a chat app's posts to the watched channel as the user `asha --portal` gave the page (`as <user>`; with none it says to type one in the Send view): **To** (`everyone`, then each agent on the channel), the text, **Send** — Return sends, Shift+Return is a new line, and Return while an input method is composing sends nothing. It sends what the Send view sends, through the same code ([`converse.ts`](../../src/portal/converse.ts)); the message and its replies appear in the chat as every message does, and the CLI's `✗` and `⚠` lines for it as notes.

## Run demo {#demo}

**Pattern demo** lists every [pattern demo](../patterns/index.md) of the daemon's checkout (`P5 · Orchestrator–workers`, …), from [`GET /v1/demos`](../architecture/index.md#apis); **Run demo** runs the chosen one exactly as its page's run block says: it reads the demos again, watches the first channel `pNN-<k>` the daemon has not used (so the team's members join as `<name>-1`, as the page's commands address them), launches the team there, then sends each scenario's messages in order as your user, an answer to an agent's question (`conversation=@previous`) sent with the conversation it answers. The chat says `demo <pattern> on channel <channel>`, each scenario as it starts, and how it ended — its steps' exit codes, as the command line gives them — and how long it took against the demo's bound (`p05-a: exit 0 in 9.3 s (bound 27 s)`; several demos end a scenario with exit 1 on purpose, such as P17's budget). Every scenario runs; a scenario stops at a step that does not settle, and the demo stops if the launch fails or the daemon is stopping, saying which. When a conversation the page sent settles, its work bubbles end. The team's agents stay online, and the chat's last note says so: `its agents stay online on channel <channel>; Stop demo ends them` ([below](#demo-stop)). Two demos are listed and cannot run here, each saying why: P25 (restart), whose test injects a fault — worker-1's container paused, then killed — that the page cannot; and P20 (checkpoint and resume), which stops and restarts the daemon, which the page cannot yet follow (<span class="badge planned">planned: portal-restart</span>). An installed release has no demo pages: the list says they come with a checkout. The sub-agents of 18 demos run on `pico-v2-q8_0`, their routers on `qwen3-8b-q4_k_m` (each page's models line names them; since 2026-10-10, `docs/plans/demo-model-pico.md`): running one loads Pico-V2, downloading its 9,028,871,552 bytes the first time. For the 13 with a router it loads Qwen3 too, and the daemon keeps both model servers until no agent needs them — after **Stop demo**, or at its own stop — about 24.6 GiB resident together at their largest in the demos' recorded runs; P3, P12, P25, P15 and P17 have no router and load Pico-V2 alone.

## Attaching files from the page {#files}

A browser gives a page a picked file's name, size and bytes, never its folder. So before anything is sent, the page checks each file, in this order, and refuses the whole message at the first refusal (`✗ <name>: <rule>`, the CLI's rule text): the name rules; the credential deny list's **file-name** entries (`id_ed25519`, `.env.*`, `*.pem`, `credentials`, …: `on the credential deny list (a file named <entry>)`, [`deniedName`](../../src/shared/credentials.ts)); over 25,000,000 bytes; more than 10 files. Then, as the CLI does: the channel's file space made ready, a `⚠` line for each cloud-granted agent before any byte leaves, the space's bounds, each file's sha256, and one upload. The notice beside the picker says it, word for word:

> asha checks each file's name against its credential deny list, and refuses a file holding asha's own credential or model-server key. It cannot check which folder a file is in, since a browser does not say: a secret file with an ordinary name, such as .docker/config.json, would be sent. The command line's file= checks folders too.

**The daemon refuses any upload holding asha's own secrets**, from the page or the command line: the running daemon's control credential, and this run's model-server key from the moment it is made. Each file's bytes are searched as they pass, and a match refuses the upload before any byte of it is copied: `✗ upload to channel <c>: 400 holds_asha_secret: <name> holds asha's control credential` ([the upload route](../architecture/index.md#apis)). **It does not catch:**

- any other program's secret;
- asha's values in another form — upper case, base64, split by a line break, compressed, or inside an archive;
- the dead credential and model-server key of an earlier daemon run (a crash leaves its `model-server.key` behind);
- agent tokens;
- a value typed into a message's text or a file's name;
- a value split across two files.

## The scene {#scene}

The watch view draws the channel as a crew of robots in the spirit of the company web site's animation (adapted from its `site/sim.js` and `site/robots.js`, which stay on the site unchanged): one robot per agent online, labelled with its handle, in the order they joined — as many as the floor holds apart: 6 on the canvas beside the chat at a 1280 px window, 10 in the demo videos' frame, never fewer than 4 — and a `+n` badge at the floor's lower left for the rest. The floor is the whole canvas, one flat colour, and every robot is drawn at one size; a robot's work bubble and card stand above it, or below its name when there is no room above (since 2026-10-16, `docs/plans/demo-scene-refresh.md` R1–R5). Everyone who posts as a user is one figure standing on the dock. A dotted arc flies from a message's sender to each addressee. What each says is shown in a bubble beside it for 4 s — two lines of at most 28 characters, a longer text ending `…` — so an agent coming online says `Hi`, and an agent about to act says `ok` ([`bubbleLines`](../../src/portal/scene-sim.ts)). Above an agent given work — a message addressed to it, or its `ok` on a message to everyone — a work bubble says `working on: <the task>` until it replies, answers, hands the work on or passes, or someone else answers the user in that conversation. Above that, an agent that asked others in a call shows a card, `collecting a/n`, each agent asked `waiting` until its outcome (`merci`, `passed: busy`, `timed out`, …), then `collected n/n`, until its work ends; a narrow scene shows the card's title only. The canvas is 420 px tall beside the chat and the chat the same height; stacked, on a narrow screen, 300 px. Boxes are kept inside the canvas; a robot's own boxes never meet (its speech stands below its work bubble, or below its card when it has no work bubble), and when robots stand close together the newer boxes move up — or down — to free space, overlapping only when the canvas has none ([`layoutBubbles`](../../src/portal/scene-sim.ts)). Each robot keeps a personal space: its body, its name label and its boxes, with 6 px to spare ([`personalSpace`](../../src/portal/scene-sim.ts)). How the robots keep it:
- A wandering robot stops short of another's space and turns away, and picks its next spot clear of the others.
- Robots whose spaces meet, because a box appeared or a robot joined, move apart.
- A robot whose space has met another's for 2 s walks out to a free spot, up to three times. If it still meets one, it gives up and wanders at its usual pace until it is clear.

Where the floor holds every space, the robots end up apart: four robots within about 12 s, the rest within a minute. The scene draws no more robots than its floor holds apart, each working (measured (`evals/probes/demo-scene-refresh-2026-10-16/capacity.json`), 2026-10-16): 6 of the 7 that fit beside the chat at windows of 1280 px or more (694 px wide), 10 in the demo videos' frame, 5 at an 1100 px window's 610 px canvas, 4 at 900 to 1000 px (490 to 550 px wide, with one-line boxes) and on the stacked 718 px canvas.

Elsewhere the floor cannot hold even the four the scene always draws (the same probe, 2026-10-16):
- an 800 px window's 430 px canvas, which holds three;
- the narrow stacked canvases, 375 px wide and under at windows under 760 px, which hold two (the 718 px one holds five).

There the robots make what room they can, and the boxes are kept apart as above where the canvas has room. The users' figure and the `+n` badge keep no space. Under reduced motion the robots stay where they first stood. *Added 2026-10-09 at the owner's request.* A robot's antenna lamp glows amber while its model is writing — from a call's first output until its end, or while the latest telemetry answer says a call of its is in flight. A robot whose agent went offline unasked is crossed with a red ✕ and stands still from that status until its next message — its greeting once restarted — clears it; if it leaves instead, it stays, crossed, for 2 s (until the next event under reduced motion) and then goes (*since 2026-10-16, `docs/plans/demo-scene-refresh.md` R8*). Nothing appears, moves between places or changes colour without an event; only idle wandering, robots making room for each other, blinking, and a crossed robot's going 2 s after its leave run on their own. Each watch draws a scene of its own, from its own events, so a second watch or a second demo in the same page draws its robots as the first does. *Corrected 2026-10-08: until then, with motion, only a page's first watch was drawn — every later one, a demo after the first included, left the scene empty, since the first scene's last frame handle was never cleared and a new loop never started ([`WatchView`](../../src/portal/watch-view.ts)'s `start`); a still scene, under reduced motion, was redrawn on each event as it is now. Found by the owner.* With reduced motion asked for by your system, the scene is one still frame, redrawn on each event, holding every open work bubble and card and the latest speaker's bubble ([`scene-sim.ts`](../../src/portal/scene-sim.ts), [`scene-draw.ts`](../../src/portal/scene-draw.ts)).

## Telemetry {#telemetry}

While a watch is open the page asks `GET /v1/telemetry` every second and shows, per agent online on the channel: its recipe, its team (`—` for a recipe launched alone) and its model; its deliveries and model calls; how long its last model call took; its calls in flight now; and its last failed span with its reason and time. The counts come from the daemon's own spans, as written to the day's trace file since the agent's first one — never from an agent's own spans, which an agent writes ([`src/daemon/telemetry/`](../../src/daemon/telemetry/index.ts)). They start at the agent's first recorded span, and go when it leaves the channel. Above the scene and the chat, the same answer names the teams and recipes on the channel: one line per team (`team crew: lead-1, helper-1`) and one per agent launched alone (`recipe hello-world: hewo-1`), in the order the agents joined.

### Stop demo {#demo-stop}

Once Run demo has ended, whether its scenarios passed or not, **Stop demo** appears beside it while the watch is on that demo's channel and an agent is on it. It is hidden while a demo runs, on a channel no demo started, and once the demo's agents are gone, however they were stopped. Pressing it sends [`POST /v1/channel/stop`](../architecture/index.md#apis) for the demo's channel, the request `asha --stop channel=<channel>` sends ([CLI](../cli/index.md#stop)):

- The daemon stops that channel's agents as its own stop stops them — each finishing the work it has started, a persisted one checkpointed first, every container gone within 70 s ([one channel's stop](../architecture/channel.md#channel-stop)) — and removes the channel's file space, killing an upload to it still in flight.
- Then it stops each model server that no agent on any channel still needs, a demo's Pico-V2 and Qwen3 among them; a later launch that needs one starts it again.
- The watch stays open: the robots leave the scene and the telemetry as they stop, and the chat gains the lines the command prints, as notes after the closing note — `stopped <handle>` for each agent, then `stopped the model server for <model>` for each server stopped. The command-line view prints them too.
- Agents on other channels, and the model servers they use, are left alone.

Once the stop is done, the button goes. A stop that fails shows its `✗` line as a failure note — the daemon's own detail when it says why (`✗ the stop of channel p05-1 failed: worker-a-1 still running after the stop`) — is reported as any failure is ([below](#failures)), and the button stays to try again (`stopDemo` in [`src/portal/watch-view.ts`](../../src/portal/watch-view.ts)).

## Stopping the daemon {#stop}

**Stop the daemon…** asks *Stop the daemon and every agent on every channel?*. On **Yes** it sends `POST /v1/stop`, clears the status lines (they were the running daemon's) and shows *stopping* while the daemon answers 503; once nothing answers it shows *stopped serving: the daemon is finishing its stop* — not *stopped*, since the daemon still stops its agents' containers and model servers after it stops serving. If the daemon still answers 90 s after the request, the page shows `--stop`'s line, from the same function (`stillRunningLine` in [lines.ts](../../src/shared/lines.ts)), naming the stop where `--stop` names the signal it sent: `✗ daemon pid <pid> is still running 90000 ms after the stop` (`--stop` prints `… after SIGTERM`). *Corrected 2026-10-02 by the portal's completion review: this said the page shows the line `--stop` prints, which ends `after SIGTERM`.* A page left open after a stop cannot reach the daemon; run `asha --portal` to start a new one.

## Failures {#failures}

Every request the page makes is bounded by the CLI's own bounds ([`src/shared/timing.ts`](../../src/shared/timing.ts)): 3 s for a short request, 60 s of silence on a stream, 260 s for an upload's answer, 30 s of silence in a download. A failure is shown in the view where it happened — never a blank or stale view — and reported to the daemon with `POST /v1/portal/errors`, which logs it as `portal.client_error` with a reason and a detail built only from the route's path, a status, an event's reason and an error's name:

| What happened | Shown | Reported as |
|---|---|---|
| A request could not be sent | `✗ request_failed: …` | `request_failed` |
| A route answered a status it does not answer on success | `✗ bad_status: … answered HTTP <status>` (an upload refusal is shown as the CLI prints it, and not reported: the daemon already logged it) | `bad_status` |
| A stream ended or was cut before it was done | the CLI's line (`✗ the daemon closed the conversation before it settled; see its log`) | `stream_cut` |
| A stream's `error` event | the CLI's `✗ <reason>: <detail>` | `stream_error` |
| A bound passed | `✗ timeout: …` (a download: the CLI's `no bytes for 30 s`) | `timeout` |
| The page's own code threw | `✗ exception: <name>: <message>` | `exception` (the name alone) |
| The daemon refused the page's credential (401) | `✗ the daemon refused this page's credential … run asha --portal to open a page that works` | never |
| The daemon is stopping (503) | `stopping: …` | never |
| The daemon cannot be reached | `✗ the daemon is unreachable …` | never — and never retried |
| A report itself failed | `✗ the failure could not be reported to the daemon …` | never |
| A failure met after the page's `beforeunload` — a reload, a navigation or a closed tab ends the page's requests, which Firefox does after `beforeunload` and before `pagehide` | as any failure | held for 3 s ([`PageLeaving`](../../src/portal/client.ts), `LEAVING_HOLD_MS`): a page gone by then never sends it — a reload leaves in 2–8 ms (measured (`evals/probes/portal-leaving-2026-10-08/README.md`)) — and a page still here (a navigation answered 204, or as a download) sends it then. What it leaves, in Firefox: a navigation slower than 3 s still reports its watch's end as `stream_cut`, and a report being sent as a navigation that leaves the page in place starts is lost, the page saying the daemon is unreachable (D64). *Added 2026-10-08: until then a reload while watching logged `stream_cut` `/v1/channel TypeError` at error level; the first fix, `0a4cadd`, stopped every report once `beforeunload` had fired, which its review found hid the failures of a page that stays.* |

To find them: `jq -c 'select(.event=="portal.client_error" or .event=="portal.client_error_dropped")' "$ASHA_HOME"/logs/daemon.jsonl`. At most ten are logged a minute; the rest are counted in one `portal.client_error_dropped` record ([logs](../architecture/index.md#logs)).

## What protects it, and what does not {#security}

- **Other web pages** in your browser cannot use it: every request to the daemon must name it in `Host` and, when sent, in `Origin`, and every control request needs the credential, which only the page's own tab holds. A page that frames the portal gets nothing: it may not be framed (`frame-ancestors 'none'`).
- **Text from agents and models** — messages, handles, file names, model output — is untrusted: it reaches the page only as text, never as markup, and the page runs no script but its own. Every response for the page carries `content-security-policy: default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'none'; form-action 'none'`, and the page loads nothing from the network.
- **Other users of this Mac** can reach the daemon's port, but not without the credential: the page's files hold none, and `portal.html` is `0600` in your `0700` `ASHA_HOME`, beside `daemon.json`.
- **Not protected:** programs running as you, your browser's extensions, and your browser's history — which can keep the forwarding address, credential included, and, if your browser syncs history, carry it off this Mac — can read the credential; any program running as you could already read it from `daemon.json`. The credential dies at the daemon's next start.
- **Not protected:** a loopback address reused. A program that once served on `127.0.0.1:<port>` and was opened in your browser — another user's included — could have left a service worker for that address; if the daemon later gets that very port, the worker could read the credential. The daemon's port is chosen afresh at each start.
- **Browsers:** the page uses only standard features every current browser has. It is tested in Chromium and Firefox; Safari is not tested.
