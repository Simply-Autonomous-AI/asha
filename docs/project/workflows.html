Workflows

How a change moves from idea to commit. Human review is optional (PRINCIPLES §21), so the checklists at the end define "done".

verified 2026-09-27gate: npm run checkrules: AGENTS.mdsources: PRINCIPLES.md §17–§21, package.json

In short

  • Every change: test first, docs true in the same commit, one adversarial review, npm run check green, commit on main with a Review: trailer.
  • Future work is built only from a ready plan.
  • Review findings are fixed, rebutted with evidence, or declined as nits — never declined for correctness, security, data loss or a principle.
  • Owner questions go through npm run decisions, not chat; shortcuts go in the debt register.

The whole flow

Planning workflow

Future work lives only in docs/plans/ (docs/plans/index.md) (PRINCIPLES §19), and nothing is implemented from a plan that is not ready — with one exception (the owner, 2026-09-29, record pattern-build-before-ready, PRINCIPLES §19): a pattern-demo plan whose only step left before ready is its premise probes on the model may have its model-free parts built, on a branch, never merged before the plan is ready.

  1. Write the plan as docs/plans/<slug>.md from the plan template (docs/plans/template.md), listed in the plans index (docs/plans/index.md) as draft: numbered requirements (R1… with MUST / MUST NOT), open questions each a TODO: naming who decides, and acceptance criteria (A1…), each an observable check naming its requirements.
  2. Plan review (adversarial, one round): are the requirements unambiguous, complete and testable, each proven by a criterion?
  3. Close the open questions: the owner answers only owner decisions (cost, product behaviour, anything user-visible, legal — PRINCIPLES §4), dated; the planning agent decides the rest, with its reason.
  4. Ready when the plan-ready checklist passes; set it in the plan and the index.
  5. Implement (in progress) through the coding, testing and documentation workflows.
  6. Completion review with the completion-review prompt: evidence in every cell of the requirement table, or it is a material gap.
  7. Done in the completing commit: criteria checked off with evidence, the completion table on the plan page, durable docs as built (badges removed), retired debt paid in the debt register (docs/plans/debt.md), the plan checked off in the index.

Coding workflow

  1. Read first: AGENTS.md, PRINCIPLES.md, the matching Architecture page, then the code itself (PRINCIPLES §5).
  2. Build once: npm install && npm run build; ./asha runs dist/ and never runs npm. Once per machine, for the browser tests in the gate: npx playwright-core install --no-remove chromium-headless-shell firefox (the pinned headless Chromium and Firefox; no gate run ever downloads them, Testing).
  3. Test first, injecting every collaborator (tests/helpers/fakes.ts, tests/helpers/daemon-fakes.ts); see it fail for the right reason, then pass.
  4. Keep the structure (§10, §11): a folder per capability under src/daemon/ with an index.ts; adapters chosen only in src/daemon/compose.ts; failures through src/daemon/log.ts; a timeout on every remote call.
  5. Rebuild before a real run: a running daemon does not reload; ./asha warns (… Run asha --stop to use this build.), and ./asha --stop picks up the new build.
  6. Commit on main at every checkpoint, never branching or rewriting history (§1; the owner, 2026-09-30, record agent-branches (c): one agent at a time changes files, on main — from 2026-09-26 to 2026-09-29 the lead had run parallel agents on local branches without the owner's consent; the 28 branches are kept until the owner says otherwise), as type(scope): summary (fix(images/memory): …, feat(cli): …, test: …), with Co-Authored-By when an AI assisted. Shortcuts go in the debt register in the same commit.
  7. Push to origin with a short timeout; if it is unreachable, note it and carry on (§2; verified):
GIT_SSH_COMMAND="ssh -o ConnectTimeout=5" git push origin main

Documentation workflow

  1. Same commit as the code (PRINCIPLES §15). Start at docs/index.md.
  2. Edit the .md, never the .html, following the documentation contract (callouts are > [!KIND] quotes such as NOTE or TIP), then npm run docs (or npm run docs -- <section>/<page>.md, relative to docs/).
  3. Mark gaps with TODO:; unbuilt work is only <span class="badge planned">planned: <slug></span> (§19). Correct visibly (§12).
  4. Check it: npm test runs tests/unit/docs.test.ts (checks); look at it in a browser, phone width too; pass the documentation checklist.

Adversarial review workflow

PRINCIPLES §18 (the owner's rule, 2026-09-27)

Every change — design, plan, code, tests, documentation — gets an adversarial review, by an agentic workflow, before it is reported done. A change that touches code goes through the review loops in sdlc/ (AGENTS.md §5); any other change gets one round, below. A plan gets two: the plan review and the completion review (§19).

  • Who: a fresh, isolated agent given the diff and the charter — never one sharing the author's context (a forked agent carries the author's assumptions), and never a person (amended 2026-10-12, the owner: "Adversarial reviews are agentic workflows, not human reviews."; this allowed "or a person").
  • Charter: (1) quality problems: defects, facts not matching the code, tests that cannot fail, docs no longer true, undeclared shortcuts (§20); (2) PRINCIPLES.md and AGENTS.md not applied, rule by rule; (3) material problems in security, observability, reliability, performance, cost or other liability (licences, privacy, legal).
  • Verify by running (§5, §14): tests, the commands the change claims, a guard broken on purpose. Each material finding names the earlier check that would have caught it (§21).
  • One round (a change that touches no code): fixes do not start a second review unless one is a new design; open-ended fault-finding never ends (PRINCIPLES §4), and the gate proves the change works.
  • Dispositions, exactly one per finding, none left open: fixed (every material finding, plus the named earlier check when cheap and general); rebutted with evidence — a command and output, a file line, a primary source ("I disagree" is not one); declined with a one-line reason when excessive, nit-picky or not material (taste, wording, speculative hardening), the author's call.

Warning

A finding about correctness, security, data loss or a principle is never declined.

The completing commit records the outcome in one of these forms (checkpoint commits before the review are fine, §2):

Review: adversarial, 6 findings (3 fixed, 1 rebutted, 2 declined)
Review: adversarial, 0 findings

Reviewer prompt template

Paste this into a fresh subagent and fill in the bracketed fields. Delete the kinds that do not apply.

reviewer prompt

You are the adversarial reviewer for one change to the asha harness repo at
<REPO PATH>. You did not write it. Find what is wrong with it; do not praise it.

THE CHANGE
- What it is meant to do: <ONE-PARAGRAPH INTENT>
- The diff: <e.g. `git diff 719dad4..HEAD` or `git diff` for uncommitted work>
- Kind: design / plan / code / tests / docs (any that apply)
- Plan, if any: docs/plans/<slug>.md

READ FIRST
AGENTS.md, PRINCIPLES.md and the principles/ and rules/ files the change
touches, docs/index.md, the checklists in
docs/project/workflows.md (section "Checklists"), and every file the diff
touches, in full, not only the changed lines.

YOUR CHARTER - report every instance of:
1. Quality problems: defects, facts that do not match the code, tests that
   cannot fail, docs that are no longer true, shortcuts not registered in
   docs/plans/debt.md.
2. Principles not applied: go through PRINCIPLES.md §1-§22 and AGENTS.md
   §1-§5 rule by rule, and name each one the change breaks.
3. Material problems in security, observability, reliability, performance,
   cost, or any other liability (licences, privacy, legal).

BY KIND OF CHANGE
- Design: is there a simpler design that reuses what exists (§7)? Is every
  new moving part justified in writing? Does anything add recurring cost?
- Plan: is every requirement unambiguous (no "fast", "simple", "support"),
  testable, and proven by an acceptance criterion? Is anything the owner
  would expect missing? Are only owner decisions left to the owner (§19)?
- Code: swallowed errors, fallbacks for impossible cases, unbounded remote
  calls or waits, global state, adapters chosen outside src/daemon/compose.ts,
  failures not routed through src/daemon/log.ts (§9, §10, §11). Would a
  failure at 3am be found by the documented query?
- Tests: does each new test fail when the thing it guards is broken? Prove it:
  break the code, run the test, restore. Assert on values and exact mock calls
  (§3). Any retry, skip, sleep or widened tolerance?
- Docs: is every claim true now? Run every command the docs show. Was the
  .md source edited and `npm run docs` re-run, with no hand edit to a rendered
  .html? Is the page linked from docs/index.md or its section index, does it
  follow docs/project/documentation.md, are gaps marked TODO:, and is
  unbuilt work only a planned badge naming its plan (§17, §19)?

VERIFY BY RUNNING, NOT ONLY READING
Run `npm run check` (or the narrowest suite that proves your point, then say
which). Run the commands the change claims work. Do not modify the repo; if you
break something to prove a guard, restore it and show `git status` is clean.

REPORT
A numbered list. For each finding: material or not, the file and symbol, what
is wrong, the evidence (command and output, or quoted line), and the rule it
breaks. For each material finding, name the earliest check that would have
caught it (a unit test, a guard, a checklist item, a rule) and whether it
exists. End with the total count and every command you ran. Say "0 findings"
only if you ran the checks and found nothing.

After the review: give every finding its disposition, add the earlier checks worth adding, run npm run check, then commit with the Review: trailer.

Decision workflow

Owner questions go one at a time through decisions/queue.json, committed so every answer has history, never as a list in chat (PRINCIPLES §4, "How to ask"; the owner, 2026-09-27). npm run decisions serves it at a 127.0.0.1 address with a random token and writes answers back.

  1. One self-contained record per decision, with any list it depends on in its details: the question, what it unblocks (blocks), two to four paragraphs of background, two to four options with trade-offs, the recommendation and why, compare scores (0–3 per criterion, 3 = best), and a flow when a mechanism is decided. Before the record is committed, search the plans for requirements an option would contradict or amend (grep -n for the rule's words, e.g. grep -n "another model\|pinned model" docs/plans/*.md), and state each in the record's context and its details, and under each option it touches (added 2026-10-08: record demo-model-pico-next first offered keeping failing demos on another model without stating orchestration-patterns R6, which forbids it). A consequence listed under one option is checked against every other option, and stated wherever it also holds (added 2026-09-27: record plugin-bundled-licences listed "the repository redistributes LGPL and GPL-licensed files" under option (a) only, though the plan made it true of (c), the option chosen). A drafted record is checked by the queue's whole test, npx vitest run tests/unit/decision-queue.test.ts, run over the queue with the record added — not by validateQueue alone, which skips the source and anchor checks — and the record is committed only when that run exits 0, the exit status read before the commit, never chained past it with ; (added 2026-10-02: a record citing an anchor in an unrendered evals/ README passed validateQueue, and was committed and pushed with the test red, 7f81afc, fixed in 8e8df26).
  2. In chat, say only how many are waiting and to run npm run decisions in the harness repo.
  3. Commit answered records unchanged first (§13), then apply each (status: answered): answer, decider and date into its plan or page (§19), and commit. An answer committed with other work is still unapplied: before reporting work done, list them (jq -r '.decisions[] | select(.status=="answered") | .id' decisions/queue.json) and apply each. Applying carries into the plan every step the record's context says the lead will take and every condition it sets, and a value the chosen option asked for but the answer left blank is asked for by a new record in the same commit (added 2026-10-11: first-live-vendor-run, answered 2026-10-02 and committed with unrelated work, sat unapplied for nine days, and its budget-scope correction and its two blank values were then missed in the first application). When applying amends a requirement, grep every criterion and requirement citing it across the plans (for agent-persistence R15, grep -n "R15" docs/plans/*.md) and fix each that the amendment contradicts, in the same commit; and apply the chosen option's words as given, narrowing none of them by analogy and widening none — a figure the option and the owner's text do not give is the applying agent's, said so under Decided, and never moves a figure the option gave (added 2026-10-10: demo-videos-size's 125 MB folder was first split into 75 and 100 MB of the agent's own) — an owner's own text is quoted, and an action taken to apply it is recorded as the applying agent's decision, never as the owner's act (added 2026-09-29: agent-calls-forged-identity's "Not clear there is any value in that test case" was first written up as "the owner removed the case"): behaviour the option does not name is left out or queued as its own record, never written as the owner's answer — and an answer is applied only to the plan or page its option names; carrying it to another plan by inference is widening too, so that question goes back to the queue (added 2026-09-28: the lead extended prompt-prefix-routing, whose option named prompt-prefix's routing rule, to agent-calls' R14, A6 and R18 in c6a9c8d) (widening added 2026-09-28: applying resume-reply-where, whose option named the asha --launch that resumes an agent and one message, extended it as the owner's answer to message commands, interactive sessions, one line per message and a new exit code; narrowing added 2026-09-28: applying login-name-refused left cli-interactive A2 expecting Olga to be refused after the conversion made it olga, and made the answer's unconditional "a line telling you the ID that was used" --verbose-only).
  4. Mark it applied in the commit that applies it: status: applied, appliedNote naming where and the commit. While this repo's server runs, stop it by its pid first, once no record is pending (added 2026-10-10: three answers applied in 1627ef3 were left answered, so the page could still change them). The lead, the plans index row and the commit message attribute to the owner only the owner's words; a requirement beyond them that the user sees is labelled the agent's and queued (added 2026-10-10: portal-demo-stop's server stop was first presented as the owner's suggestion).

Two writers, one file: the server writes answers, an agent writes records. An agent edits queue.json only while this repo's server is not running, re-reads it just before writing, and writes it whole (temp file, then rename). Other repos run the same server with the same command line, so a server is this repo's only if its working directory is this checkout: list them with for p in $(pgrep -f decision-queue/server.mts); do lsof -a -p $p -d cwd -Fn; done, and stop one by its pid, never with pkill -f (added 2026-09-29: a pkill -f meant for the harness's server also stopped another repo's). The gate checks every record's shape and cited sources (tests/unit/decision-queue.test.ts).

The server, tools/decision-queue/server.mts (Node built-ins only; tests (tests/unit/decision-queue.test.ts)) with tools/decision-queue/page.html, whose API accepts only requests with the token and a Host naming the listener, against other OS users and web pages in the owner's browser (cross-site requests, DNS rebinding). The token changes every run, passes through an owner-only temporary file, and leaves the address bar once read.

Warning

It does not protect the file from programs running as the owner, which can edit queue.json directly.

Debt workflow

A sub-optimal implementation that keeps the project moving is acceptable; an untracked one is not (PRINCIPLES §20).

  1. Register it in the same commit — a commit recording a FAILED run under a remedy rule names the entry it registers or extends, in its subject (… — FAILED (D<n>)), and adds or extends that entry in the same commit, the entry naming the run's commit and results file; a script that commits run results stops on a failure for this, never commits the results file alone (added 2026-09-29: the rainbow's failing A11 runs were committed without one, D37; sharpened the same day after patterns-phase-2's eight FAILED runs were committed with their results file alone, three of them after D39 existed — never rewrite such a commit, PRINCIPLES §1: the entry names the run instead, as D39 does) — in the debt register (docs/plans/debt.md): next id (D1, D2, …), what and where (deep links), why accepted, its cost while it stays, the payoff, the date — and, unless a plan retires it, its id on the plans index's "Open debt with no plan yet" line, with the register's counts (added 2026-09-29: model-streaming registered D38 without the index line, and the docs guard went red on the commit that recorded its gate). An entry that accepts a behaviour — and a probe's record or a decision record that reports one — lists under its cost every gate scenario that behaviour fails, and every failure mode its recorded attempts show, read from the rounds or the transcript, not the score or the checker's first line (extended 2026-10-08: the demo-model-pico probe called a planner's 17 identical calls, stopped by the post budget, a budget overrun rather than a loop; added 2026-09-29: D31 accepted a routing behaviour and did not say that it failed the agent suite's off-role; D30 described one task-shaped case as a hand-off when its recorded rounds end the turn ToolCallInvalid, which takes an agent off its channel).
  2. Pay it off through a plan naming the ids under "Debt retired"; its completing commit marks them paid — only when the evidence covers everything the entry lists under its cost and "still open"; what remains is narrowed into the entry, which stays open. A change that builds what an entry's payoff names re-reads that entry in the same commit (added 2026-09-29: agent-calls proposed D24 paid while the model still relayed first, and D24 said the routing step was not added after it was).
  3. An undeclared shortcut found in review is material: fix it or register it. A trade-off a code comment states — a false report rather than a lost one — is a shortcut: it gets its entry and a line in the durable page that describes the behaviour, in the same commit (added 2026-10-08: the portal's report hold stated its Firefox cases only in client.ts; found by its second review).

The hard floor

An exploitable security hole, data loss or a swallowed error (§11) is fixed, never registered as debt.

Checklists

With the gate and the reviews, these are this repo's automated assurance (PRINCIPLES §21); each item is checked by running or reading something. When a defect escapes, sharpen the item that should have caught it; delete items that no longer earn their place.

Plan ready

  • From the template (docs/plans/template.md), every section present, listed in the plans index (docs/plans/index.md).
  • Requirements numbered, MUST / MUST NOT, no ambiguous word ("fast", "simple", "support", "etc.").
  • Every retention, size, time or rate word has a number and a criterion that crosses it; a pattern plan projects docs/plans/orchestration-patterns.md R11(h)'s demo gate-time sum from its scenarios' estimates and says what follows when it passes 600 s (added 2026-09-29: patterns-phase-2's first draft left the sum to its completion review, though its own estimates crossed it). Every computed bound is evaluated at its extremes (0 and its maximum) — a layout or motion rule at every size the page can produce, with the most items it draws, saying what happens where the rule cannot be met (added 2026-10-09: portal-scene-chat R5c was swept only at roomy canvases, and on the portal's stacked 300 px canvas its robots raced through each other for the whole watch) — and every wait bound is compared with the longest legitimate duration of what it waits for (a recipe's messageTimeoutMs, a turn's chained model calls), the client's own bound included — the page's 3,000 ms for a JSON request, STREAM_IDLE_MS for a stream (added 2026-10-10: portal-demo-stop's R1 answered one JSON body after a stop of up to about 70 s) (added 2026-09-28: agent-persistence R10's post-checkpoint grace, the whole seconds left, was 0 s after an ack at 64.9 s — a SIGKILL logged as a loss — and its 65 s ack wait was shorter than the memory recipe's 120 s turns). A step added to a stop path cites the stop constants (src/shared/protocol.ts; timing.serverStopMs in src/cli/main.ts), names every caller of the stop it changes (grep -n "stopRecord(\|stopContainer(\|runtime.stop(\|daemon.stop(\|stopDaemon(" src; and, for a new trigger of the daemon's stop, how the process then exits — src/cli/main.ts awaits runCli at top level, so a promise nothing settles exits 13 (added 2026-10-01 by portal's plan review); stopContainer added 2026-10-01: extension-modules' re-read listed the callers of stopRecord and missed disconnect, which calls stopContainer directly), every timer or background job that takes a lock or resource the stop needs (and how the stop ends it), and what happens when a second stop reaches an agent already stopping, and sums its deadline, written out, against serverStopMs and every other plan's stop requirement (added 2026-09-28: agent-persistence R10 put a 30 s ack wait in front of an agent drain that was already 65 s, past the CLI's 90 s, and against persistent-macos R20's schedule; callers added 2026-09-29: its amendment missed disconnect's stop of one agent and a team rollback racing the daemon's stop).
  • Every requirement named by a criterion, and every MUST in it mapped to an assertion of a named criterion of this plan or of a plan already built (added 2026-09-29: agent-persistence's bounded-stop MUSTs were tested only by a draft plan's criterion) (added 2026-09-28: agent-persistence R10's "stop delivering" had none, and hid a second turn started during the stop); every criterion a command or test with its expected result, run once against today's tree, and the plan page records each result (added 2026-10-11: two plans were set ready with no such record), passing or failing for the stated reason. Every event or field a criterion or requirement names is defined in a requirement or in src/shared/protocol.ts, and every field a requirement reads comes from a record the plan lists (added 2026-09-28: agent-persistence A8 expected a settled event nothing defined, and R8 read a previousHandle no record held). For every new variant of a union, the Inventory lists each exhaustive consumer (const unknown: never) and what an older CLI or daemon does on meeting it (added 2026-09-28: a settled ConversationEvent crashed ConversationTracker.handle, and every older CLI's); for every new error class, the function that maps errors onto such a union (classify in src/daemon/agents/index.ts), so the error never falls to a catch-all such as internal (added 2026-10-02: decider-tool's launch refusal would have reached users as ✗ internal: …, found by its amendment's review).
  • Every agent scenario a plan specifies is traced turn by turn: an agent's turn sees one message (the user's input, a call's question, or a gather with the message its call came from; channelTurn in src/agent-sdk/channel.ts) and the roster fixed when the turn started, so each value its reply, call or tool call must hold is shown to be in that message, in a file it reads back, or in a harness change the plan names; Code change

  • Tests first for every added, changed or deleted logic; each new guard seen to fail naming the offender (§3); every limit or bound (a size cap, a timeout, a count) crossed by a test — a name or path at its maximum length included wherever it is joined into another name or path, such as a partial file or a suffix (added 2026-09-30: agent-files' completion review, finding 3, a 242-byte returned name crashed the CLI). A timer or expiry on a record is cleared or re-checked at each change of that record's state (finding 1: a claimed upload still expired). Every wait — on a stream, an event or another connection, not only a remote call — has a bound, and a test where what it waits for never comes while the stream stays healthy: heartbeats keep an idle bound from firing (added 2026-09-28: cli-interactive's /watch on waited for a reply on the channel view with no bound, since the view's heartbeats kept it alive) — including a peer's keep-alive: a bound on a stream is reset by what it waits for, never by a read, a comment or a ping (added 2026-09-29: model-streaming's gateway re-armed its idle bound on every network read, so llama-server's : pings every 30 s could hold a stalled call forever).
  • Every failure through src/daemon/log.ts (tools outside the daemon log structured lines to stderr). No empty catch, floating promise or error turned benign; every catch, client code included, names its error and shows the real message (§11). A rule that stops a failure being reported or logged is tested where its trigger fires and the failure is real, which is still recorded (added 2026-10-08: the portal's first fix of a reload's false report stopped every report once beforeunload fired, and a page that stays after it — a navigation answered 204 — never reported again; found by its review).
  • Run-time data files validated where read, the committed copy in the gate. A file a process and an agent both write names who writes it, when, and how a lost update is prevented.
  • An explicit timeout on every call leaving the process; streams bounded by inactivity. Expected external failures return { ok: false, reason }; throwing only for violated invariants (§11). Work the daemon starts in the background — a request not awaited by the call that began it — is also ended by the stop (abandoned, logged at warn) and waited for before the model servers stop, never only waited for (added 2026-09-29: D44's prompt-store request could hold a stop 55 s).
  • A check that selects or filters files by what git reports is tested against every way git can hide a file from it: an untracked or machine-local ignore file, skip-worktree and assume-unchanged, local config (core.fileMode), a link at or above a path, an inherited GIT_DIR, and a listing command that fails with empty output (added 2026-09-29: demo-selector's code review found four of these that selected a changed demo once).

Review

  • The reviewer did not write the change, shares none of the author's context, ran the checks, listed the commands, and restored any guard breakage.
  • Every finding has one disposition, none open, none declined on correctness, security, data loss or a principle.
  • Every material finding names its earlier check; the cheap, general ones are added in this change (§21).
  • A completion review's requirement table is on the plan page, evidence in every cell.
  • Third-party code, network egress or actions with external effects come with a threat model: where egress is enforced (not only routed), supply chain, isolation of secrets, prompt injection and dangerous capability combinations, data leaving the machine, irreversible actions. A module's is on its page (its secrets, its egress, injection through its output, its consequential actions, what an agent could do with it), tested against fakes only, its cost approved in its manifest before any live call (added 2026-10-02, extension-modules R22).
  • Every "holds today" or "built" claim in a durable doc was verified by running it (§14); every recorded objective has a measurable definition or a TODO for one.
  • Every decision record is decidable alone: no bare identifier, every term explained, every list it depends on in its details; a record whose option weakens an existing rule quotes the owner's words the rule came from (added 2026-10-01: portal's portal-attachments draft explained the credential deny list without the owner's "it can't upload any local credential files").

  • The docs are true (documentation checklist); a completed plan is checked off with its evidence, and a search of the plan page for partial, waits, not built, open and in progress finds none still said of a checked criterion, a step or the plan itself (added 2026-09-29: cli-interactive's A8 was checked off still labelled "partial", found by its completion review). Every owner decision the plan applied is marked applied in decisions/queue.json, naming where it went (added 2026-09-29: prompt-prefix reached its completion review with two answered records never marked applied).
  • Every shortcut is in the debt register (docs/plans/debt.md); retired debt is marked paid.
  • Committed on main, with the Co-Authored-By trailer when an AI assisted.
  • A push to origin was attempted; if unreachable, noted in one line (§2).
