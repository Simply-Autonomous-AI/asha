Models

Every model is pinned by a catalogue entry, verified into a content-addressed cache, served on the host by llama.cpp's llama-server, and reached only through the daemon's gateway.

verified 2026-09-27pinned values read 2026-09-26recurring cost: $0 (local inference)migrated from docs/models.md on 2026-09-27.

In short

  • A catalogue entry is the pin: a repo, a 40-hex revision, and a size and sha256 for every file.
  • Files are downloaded into a staging directory and each is verified as soon as it arrives; the first bad file stops the download and the cache is untouched. One rename promotes a complete download.
  • One llama-server per model on 127.0.0.1, each requiring a key only the daemon holds (model-server.key, 0600), which the gateway sends. The gateway returns failures as data: timeout, unavailable, upstream_error, bad_response, truncated.
  • A chat is streamed from the model server, bounded by inactivity (a 55 s queue bound and a 22 s idle bound, set from measurements), and its output published as it is generated: model_delta and model_done on the conversation's stream and the channel watch.
  • memory uses qwen3-8b-q4_k_m: 18 of the 19 original routing cases (at d8350f0 and again at cb63366, llama.cpp 0.5.0); no smaller model passes more than 16. hello-world used it too until the owner moved it to pico-v2-q8_0 on 2026-10-12.
  • Embeddings use qwen3-embedding-0.6b-q8_0, apache-2.0 declared only in its model card.

The pipeline, end to end

At launch, AgentSupervisor (its private launch) loads the recipe's chat model entry, has the store ensure it is cached and the server ensureServing it, repeats both for any embeddingModel, and only then builds the image and starts the container. The catalogue entry (catalogue/<id>.json) is the pin (AGENTS.md §3).

Download and verification

HuggingFaceModelStore.ensure(entry) is the only writer of the model cache (AGENTS.md §3), and follows PRINCIPLES §13: write to a name nobody else holds, promote on success.

  1. Address by content. The cache directory is <modelsDir>/sha256-<tree digest>/ (by default models/sha256-<tree digest>/), the sha256 of the sorted path\0sha256\n lines of the entry's files (treeDigest). A directory that exists is complete: a cache hit (model.cache_hit, status cached).
  2. Lock. <modelsDir>/.lock, a pid lock (src/daemon/process/pid-lock.ts, acquirePidLock). A dead holder's lock is cleared (lock.stale_cleared); a live holder's makes it throw LockHeld at once. With the lock, the store checks the cache again.
  3. For each file in turn, fetch https://huggingface.co/<repo>/resolve/<revision>/<path> into <modelsDir>/.staging-<12 hex>/ (opened with wx, hashed as it streams; model.file_downloading), then verify it: the byte count must equal the pinned size (else size_mismatch) and the sha256 the pinned sha256 (else ModelDigestMismatch, fatal, never retried). No bytes for stallTimeoutMs (60,000 ms in productionDependencies) aborts as stalled.
  4. Promote with one rename(staging, dir) (model.downloaded, status downloaded). The staging directory is removed in a finally, success or not.

src/daemon/model-store/index.ts — treeDigest

/** sha256 over the sorted `path\0sha256\n` lines of an entry's files. */
export function treeDigest(files: readonly CatalogueFile[]): string {
  const lines = [...files]
    .sort((a, b) => (a.path < b.path ? -1 : a.path > b.path ? 1 : 0))
    .map((f) => `${f.path}\0${f.sha256}\n`)
    .join('');
  return createHash('sha256').update(lines).digest('hex');
}

The code and its comment disagree

A comment in ensure says "another process may have completed the same download while we waited", but acquirePidLock never waits: it throws LockHeld when the holder is alive. The holder's pid is checked with isAlive, so a second ensure in the same daemon during a download also gets LockHeld.

Serving on the host

Models run on the host because colima's VM has no Metal GPU (why); a container reaches them as host.docker.internal (ColimaRuntime.hostAddress).

  • One server per model. LlamaCppServer.ensureServing(entry, cached) runs one llama-server per catalogue entry and reuses it for every agent that needs it.
  • The binary. Before the first launch, ensureHostTool (src/daemon/host-tools/index.ts) runs llama-server --version, and if that fails, brew install llama.cpp. Installed here: 0.5.0 (build 11146, 7fe450e19): Homebrew upgraded it from build 8130 on 2026-09-27 (Cellar install receipt; llama-server --version). It changed forced tool calls (gateway).

AspectHow
Slots and contextA chat model's server runs 4 slots (CHAT_SLOTS), each with its own serve.contextSize tokens: --parallel 4 --ctx-size 4×contextSize, which llama.cpp 0.5.0 serves with a KV cache per slot (n_ctx_slot = 8192, kv_unified = 'false' in its log). Until 2026-09-27 it passed only --ctx-size, and 0.5.0 then made 4 auto slots share one unified pool of that size: four concurrent turns of 2,127 prompt tokens all failed with HTTP 500 "Context size has been exceeded", and all four succeed now (≈20.6 s), measured that day on qwen3-8b-q4_k_m with the daemon's flags (D17). The cost is memory: that server's resident size went from 6.2 GB to 9.8 GB. An embedding model's server keeps one context of serve.contextSize.
Prompt cacheA chat model's server gets CHAT_CACHE_ARGS: --cache-prompt --cache-ram 8192 --cache-idle-slots --cache-reuse 0 --slot-prompt-similarity 0.10, each explicit so LLAMA_ARG_CACHE_PROMPT, LLAMA_ARG_CACHE_RAM, LLAMA_ARG_CACHE_IDLE_SLOTS or LLAMA_ARG_CACHE_REUSE in the user's environment cannot change caching (the arguments win: probe A5, records (evals/probes/prompt-prefix-2026-09-28/README.md)) and a llama.cpp upgrade cannot move the slot-selection threshold. What 0.5.0 does with them (llama.cpp tools/server/ at 7fe450e19, read 2026-09-28): a slot keeps the longest common prefix of its previous prompt and the new one and processes only the rest; a request goes to the idle slot whose cached prompt shares the longest prefix with it when that exceeds 10 % of the prompt, else the least recently used; a slot's state is saved to a host-memory store of up to CHAT_CACHE_RAM_MIB (8,192 MiB, the owner's answer of 2026-09-28, decision model-server-memory (a)) and restored to another slot. --cache-reuse 0 keeps chunk reuse off: it would shift KV computed under another agent's handle or another user's memory into a prompt. Agents' requests are ordered to share a prefix so these hit (the shared prefix). Prompt caching can change greedy output, since logits are not bit-identical between batch sizes (llama.cpp README); see determinism. A recipe's or catalogue entry's chat may not set the per-request fields that change caching or slot choice — cache_prompt, n_cache_reuse, id_slot, message_delimiters (CACHING_FIELDS in src/daemon/definitions/index.ts) — and fails to load if it does.
Prompt storeAfter a recipe's first answered chat call on a chat model's server, the daemon asks that server once to store its idle slots' prompts (storePromptOnce in src/daemon/agents/index.ts, storeIdlePrompts in src/daemon/model-gateway/index.ts): POST /tokenize {"content": "."} (no special tokens), then POST /completion with those token ids as the prompt and "n_predict": 1, each with the key and a bound of PROMPT_STORE_BOUND_MS (the chat queue bound, 55,000 ms). It is not awaited by the call that triggered it, not sent once the daemon is stopping, and abandoned when the stop begins, which then waits for it to end (tests/unit/daemon-stop.test.ts, tests/unit/agents.test.ts; over HTTP, tests/integration/daemon.test.ts). Why (D44, docs/plans/prompt-prefix.md, amendment 2): 0.5.0 saves idle slots to the host store only when a task starts (--cache-idle-slots), and one agent after another of a recipe all take the slot holding the shared prefix, so that slot is never idle when a task starts and the store stays empty; the first time two agents call at once, the second lands on an empty slot and computes its whole prompt (measured 2026-09-29: 1,923 tokens in 4.6 s), and the first, batched with it, waits as long. The request's prompt shares no first token with any chat prompt, so it goes to the least recently used slot — an empty one while there is one — and the warm slot, idle, is saved; a later request on an empty slot restores the prefix from the store. It is a token array because a text prompt gets BOS on a model that adds one: Ministral 3's GGUF sets tokenizer.ggml.add_bos_token, and a text "." then shared BOS with the warm slot (1 of 2 tokens, over the 10 % threshold), took that slot, and left the store empty again (measured 2026-09-29; tokenize_mixed adds BOS only when the prompt's first element is text, llama.cpp tools/server/server-common.cpp at 7fe450e19). Logged: model.prompt_stored (model, recipe, ms) once the server has answered — which says the task ran, not what was saved —, model.prompt_store_abandoned (warning) when the stop began first, or model.prompt_store_failed at error level with its reason (timeout, unavailable, upstream_error, bad_response, or internal for a harness defect); never retried.

The watchEvery llama-server runs under WATCH_SCRIPT (src/daemon/process/launcher.ts, dieWithParent; docs/plans/idle-shutdown.md R5), a /bin/dash (WATCH_SHELL) the daemon starts as its own process group — not /bin/sh, which on macOS is bash 3.2: sent a burst of 30 stop signals on a loaded Mac, 9 of 240 bash watches died by a signal (SIGSEGV, mostly) before passing the stop on and 6 hung, leaving 8 servers running, against none of 240 under dash (2026-10-16, evals/probes/watch-shell-2026-10-16/) — whose standard input is a pipe only the daemon holds and never writes. The watch starts llama-server with no standard input, prints asha-watch: pid <n> (llama-server's own pid) as its first line, and waits. The daemon gone — however it ended, SIGKILL included, the kernel closes its end of the pipe — or a stop (SIGTERM, SIGINT or SIGHUP to the watch): one SIGTERM to llama-server at once, then SIGKILL 8 s later if it still runs, so it is gone within 10 s; the watch exits with its status and ends its helpers. Exactly one SIGTERM, because llama.cpp 0.5.0 takes a second as "Received second interrupt, terminating immediately." (libllama-server-impl.dylib, read 2026-10-15): the daemon signals the watch alone, and only a SIGKILL goes to the whole group. No pid is polled: the watch is llama-server's parent, so its pid cannot be reused while the watch waits on it. A stop before llama-server has started means it never starts (exit 143); one in the instant between its fork and its exec can be lost, and the SIGKILL ends it. A watch that does not lead its own process group refuses to run (exit 125). A server is not ready until its pid is named: model_server.ready logs pid (llama-server's, what the sweep selects) and watchPid. Tests: tests/unit/process-watch.test.ts (real processes: a stand-in daemon SIGKILLed, one SIGTERM, the SIGKILL timer, a burst of 30 stop signals to 16 watches at once, each guard seen failing), tests/eval/lifecycle.eval.test.ts (a real daemon SIGKILLed, its llama-server gone within 10 s).
Idle unloadA model server with no call holding it whose last call ended — or, never called, which became ready — ASHA_MODEL_IDLE_MS ago (default 900,000, 15 minutes) is stopped by the daemon's lifetime check, model_server.unloaded_idle (model, idleMs), freeing its 5–13 GB. Every chat and embedding call takes a lease on its model for its whole duration (lease; onLeased in src/daemon/agents/index.ts), so a held server is never unloaded — nor stopped by stopIdle — and a model unloaded since its agent launched is started again by the next call, logged model_server.reloaded with the ms it waited. That wait is inside the call's first-chunk bound, the queue bound (55,000 ms, below): a reload took 0.6–15.2 s on this Mac, median 1.6 s (record (evals/probes/idle-shutdown-2026-10-15/reload-times.json)), and the queue's longest recorded first chunk 32.7 s, so the daemon's bound still ends an agent's call, naming its cause, before the SDK's 60 s. A wait the agent's exit or its request closing cuts short ends the call as either would a call that reached its model; a lease that comes after is released at once, and a start that fails after is logged model.start_failed. The prompt store holds the very server its call reached (holdServer, by server number, which a restart on the same port does not reuse) and never starts one: that server gone, the store is skipped, model.prompt_store_skipped.

Calling a model: the gateway

An agent calls POST /agent/v1/model/chat or POST /agent/v1/model/embed with its bearer token (HarnessClient.chat, HarnessClient.embed in src/agent-sdk/index.ts; an unknown token gets 401). The daemon validates the body (parseChatRequest / parseEmbedRequest, closed; a requireToolCall chat must not end with an assistant turn, since the prefill opens one) and makes one call to that agent's model server, with the server's key as Authorization: Bearer <apiKey> (ModelEndpoint.apiKey); only the daemon holds the key, so the gateway is the only way in. A chat is streamed from the model server and its output published as it is generated (below); the agent still receives one whole answer.

  • Chat. {messages, maxTokens, tools?, requireToolCall?}: maxTokens an integer in 1..4096, at most 16 tools, and requireToolCall: true needs tools, is sent as tool_choice: "required", and opens the assistant turn with the entry's toolCallStart (why: the warning below) — unless thinking is on (below). Sampling is chatDefaults: { ...record.entry.chat, ...record.recipe.chat } (the recipe wins). The merge is shallow: a recipe that sets chat_template_kwargs replaces the entry's whole object, not key by key. The harness's own fields — model, messages, max_tokens, tools, tool_choice, stream: true, stream_options: {include_usage: true}, return_progress: true — are written after, so no definition can set them. Returns {ok: true, text, toolCalls} to the agent; tool-call arguments are parsed from JSON and every call must carry an id. Beside it the daemon gets the stream's figures (ChatStats in src/daemon/model-gateway/index.ts): the usage chunk's prompt_tokens, completion_tokens and prompt_tokens_details.cached_tokens, the time to the first output, and the chunks received; the agent never sees them.
  • Embeddings. {texts, purpose}: 1..64 non-empty strings, purpose "query" or "document"; a recipe with no embeddingModel gets a 400. A query is written with the entry's embed.queryTemplate ({text} replaced); a document is sent as it is. One vector per input, each exactly embed.dimensions long, placed by the server's index, not by position. Not streamed (embeddings are not incremental); bounded by the daemon's chatTimeoutMs, AGENT_CHAT_TIMEOUT_MS (60,000 ms), wall clock.

The stream, and its bounds

llama-server answers a chat as server-sent events: data: <json> chunks — prompt_progress chunks while it reads the prompt, output chunks (choices[0].delta: reasoning_content, content, or a fragment of a tool call's arguments, the first naming the call's id and function), exactly one chunk with a finish_reason, one usage chunk with choices: [] — then data: [DONE] (StreamReader in src/daemon/model-gateway/index.ts). The gateway assembles it into the same ChatResponse the whole answer would give. A stream short of that — no [DONE], no finish chunk, no usage chunk or one without all three counts, anything after [DONE], a line that is not SSE data or not JSON — is bad_response, never a shorter answer; a chunk reporting an error is upstream_error.

A chat is bounded by inactivity, not wall clock: every data: chunk of the stream, progress chunks included, is activity; a comment is not — llama-server writes a : ping every 30 s by default (--sse-ping-interval, per llama-server --help on 0.5.0, build 11146, read by the code review of 2026-09-29), and a ping must not keep a stalled call alive. (Corrected 2026-09-29, before merge: this said every network read was activity, and the code did so; the review found a ping would then reset the bounds.) A throw from the daemon's own delta sink is a harness defect, re-thrown (DeltaSinkFailed, answered 500 and logged http.handler_failed), never reported as a model failure.

Measured twice on 2026-09-29, at clean commits e241518 and 6cafba3, on an Apple M4 Pro with 48 GiB, llama-server 0.5.0 (b11146), qwen3-8b-q4_k_m with 4 slots: ten concurrent calls of 1,174 prompt tokens and one of 5,925, each with return_progress — the last first chunk at 31,774 and 32,670 ms (the eleventh call waiting for a slot), the longest gap inside a stream 5,531 and 5,411 ms (evals/probes/model-streaming-2026-09-29/measure-e241518.json, evals/probes/model-streaming-2026-09-29/measure.json, evals/probes/model-streaming-2026-09-29/measure.mjs). The plan reviewer's capture of 2026-09-27 saw a gap of 11 s with other llama-servers sharing the GPU (docs/plans/model-streaming.md, capture 5; no committed record, kept because it can only widen the bound), so the idle bound is 22,000 ms; the queue bound's rule gives 66,000 ms, capped to 55,000. (Corrected 2026-09-29: until these measurements the bounds were a provisional 54,000 and 22,000 ms, from capture 5 alone.) Eleven calls on four slots is near capacity (D19): a burst whose wait for a slot passes 55 s fails timeout, naming the queue bound. The routing eval, which has no SDK bound, sends one call at a time. The upper limits stay: the SDK's chatTimeoutMs, AGENT_CHAT_TIMEOUT_MS (60,000 ms), bounds a call as the agent sees it, and the recipe's messageTimeoutMs the whole turn; a call longer than 60 s is cut by the SDK by design, since the reply targets are 4,000 and 5,000 ms at p95 (docs/plans/enterprise-targets.md). The agent suite fails any chat call over 75 % of the SDK's bound (Testing).

When the agent's own request closes before the answer (its bound passed), the daemon aborts the model server's request, freeing the slot, and the call ends timeout with the detail the agent's request closed before the answer. When the calling agent's container has exited, the call ends at once as unavailable, abandoned: the calling agent exited, and is logged model.call_abandoned at warn; so is a call whose request closed while the daemon is stopping its agent, since the container's exit and its connection closing come in either order. Whatever ends a call, the model server's request ends with it.

Deltas

While a chat streams, each piece of output goes to the conversation it belongs to — derived from the call's validated traceparent (AgentRecord.conversations, filled beside record.traces in connect), never from the agent — as a model_delta event {handle, conversation, call, seq, part, text}: call is the call's asha.chat span id, seq counts from 0 per call, part is thinking, text or tool_args (with index and name). Then one model_done {handle, conversation, call, outcome}, ok or the failure reason, published from a finally, so exactly once per call and after its last delta. Both go to the conversation's stream and to every watcher of the agent's channel (Channels and agents); a call refused before the model server's request (a trace that is no conversation delivered to the agent, or a tool outside its own) publishes nothing. No log record carries delta text.

Thinking

Whether a model thinks is a recipe setting, off by default: thinking is on only when the merged chat.chat_template_kwargs.enable_thinking is exactly true. Every Qwen3 entry sets it false; no recipe in recipes/ turns it on. When it is on, the gateway sends no toolCallStart prefill (with the prefill the model does not think), streams reasoning_content as part: thinking (it is never part of the reply text), and a required call cut by finish_reason: length is truncated with a detail that says whether the cut came while thinking. Without the prefill a forced call may again follow free text (the warning below), so a recipe turns thinking on only after the routing eval and the timing targets are re-run with it on (model-streaming A7).

Expected failures come back as {ok: false, reason, detail} (PRINCIPLES §11), never as exceptions, from ModelFailureReason in src/shared/protocol.ts:

Log records

The supervisor logs each call: model.chat / model.embed at info, model.chat_failed / model.embed_failed at error, with handle, channel, model and duration (the 3am query). A chat's record also carries the stream's figures (since model-streaming, 2026-09-29): ttfcMs (from sending the request to the first chunk of output, progress chunks excluded), chunks, promptTokens, completionTokens and cachedTokens — null where the stream did not get that far. A model.chat also carries toolCalls (since 2026-09-29): the names of the tools the model called in that response, in order — never their arguments — so which tools a turn used can be read outside the agent (the agent suite's two-models scenario reads it; AgentSupervisor.chat in src/daemon/agents/index.ts). model.chat_failed's error keeps its detail, which can hold up to 200 characters of the model's output. Each call is also an asha.chat or asha.embed span, which ends with the call's reason when it fails (traces).

Hosted models: providers

A recipe may name a hosted model in place of a local one: "model": "<module>/<name>", a model a ModelProvider module declares. The agent's code does not change — its chat and embed calls go through the same routes — but the daemon sends them to the provider's container (providerChat, providerEmbed) instead of llama-server: no download, no model or model_server launch phase, no tool-call prefill, no return_progress, no prompt-store request. A request that requires a tool call names requireToolCall, which the provider sends as the vendor's own forced tool choice; the stream keeps the gateway's bounds (55 s to the first chunk, 22 s between chunks) and events, and the vendor's token usage settles the meter. A recipe naming a hosted model is cloud-granted: every prompt leaves the machine, so it is never used by an image that keeps memory (memory).

Pinning a hosted model (extension-modules R20; AGENTS.md §3 for hosted models): the manifest names the vendor's exact model id as its card gives it, and the schema refuses an alias that moves (latest), an inference profile (a us., eu., apac. or global. prefix) and an ARN; it records the card's URL and launch date, the prices with their source and date, and the vendor's terms and data-retention policy, each by URL and date read. The docs guard fails once a price was read more than 90 days before the day it runs. Before any live chat, the opt-in live check reads the model's lifecycle state and refuses anything but ACTIVE. The one hosted model so far is bedrock/ministral, mistral.ministral-3-8b-instruct — the same family as the local ministral-3-8b-instruct-2512-q4_k_m, so a local and a hosted run compare like for like.

Adding a model

  1. Read the model's API record for the exact revision: curl -s 'https://huggingface.co/api/models/<repo>/revision/<sha>?blobs=true'. Take the revision sha, and each file's size and lfs.sha256.
  2. For files that are not LFS (licence, config, tokenizer JSON), download them at that revision and compute the sha256 yourself.
  3. Read the licence at that revision, for that repo (PRINCIPLES §12). It must be commercially permissive; with no licence file, the card declaring it is pinned as the licence record (AGENTS.md §3).
  4. Write catalogue/<id>.json, and add a section here with every value's source and date.
  5. Point a recipe's model (or embeddingModel) at the id; run npm run check. For a chat model meant to replace qwen3-8b-q4_k_m, also run the routing eval — npm run build && node dist/evals/routing/run.js [model-id ...], usage from the header of evals/routing/run.ts — and commit its result file.
