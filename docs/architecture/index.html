Architecture

asha is one command and one daemon on the user's desktop. The daemon runs agents in colima containers, carries a named channel between them and the user, and brokers every model call to llama.cpp on the host.

verified 2026-09-27 against the source; control-api-auth sections at 222a6c5gate: 05555b1asha 0.1.1source: src/, images/; migrated from docs/architecture.md on 2026-09-27.

In short

  • Everything binds to 127.0.0.1, and no cloud service is involved unless a recipe grants a module that reaches one — then only that module's container reaches it, through the egress proxy, and only its manifest's hosts.
  • An agent comes online in five phases: container runtime, model, model server, image, agent.
  • Two HTTP APIs share one listener, behind one guard: Host and Origin must be the daemon's own, then /v1/ needs the control credential from daemon.json and /agent/ a live agent token. Every llama-server requires a key only the daemon holds, and an agent container reaches only the daemon's port on the host.
  • Channels, conversations and tokens live only in the daemon's memory. One jq query over logs/daemon.jsonl finds every daemon failure.
  • Every conversation is one OpenTelemetry trace: agents send their spans to the daemon over OTLP/HTTP, the daemon adds its own, and both are written to logs/traces-<UTC date>.jsonl (traces).
  • The gate is green at 05555b1: unit 484, integration 41, agent suite 35, eval 10.

The command

asha is run as ./asha from the repo. user= says who you are (users). Every command and flag is in the CLI reference; the CLI guide shows real output.

asha [user=<id>] [recipe=<r>] [channel=<c>] [to=<handle>] message=<text>
asha --launch recipe=<r> [channel=<c>]
asha --watch [channel=<c>]

./asha recipe=hello-world message="Please say: Hello World."   # → Hello World.
./asha to=hewo-1 message="Please say: Hello World."            # straight to that agent
./asha --watch                                                  # in another terminal
./asha --stop

The gate is npm run check: typecheck, unit tests, integration tests, the agent suite, then the eval, which runs the first command above and asserts the exact reply.

The two APIs

Both share one loopback listener: the control API (/v1/, the control credential on every route) and the agent API (/agent/, the agent's bearer token on every route). The same listener serves the portal's page, which needs no credential (below). src/shared/protocol.ts is the contract (Routes); src/daemon/server.ts routes them.

The guard (guard in server.ts) runs before any route, and reads nothing else about the request first:

  1. Host must be exactly 127.0.0.1:<port> or localhost:<port>, where <port> is the daemon's; on /agent/ also host.docker.internal:<port> (ContainerRuntime.hostAddress), the name containers use. A missing Host is refused too (the server is created with requireHostHeader: false, so Node does not answer it first). Otherwise 403.
  2. Origin, when sent, must be exactly http://127.0.0.1:<port> or http://localhost:<port> (Origin: null included). Otherwise 403. These two stop a web page reaching the daemon through DNS rebinding or a cross-site request.
  3. /v1/…, any path, a route or not, needs Authorization: Bearer <credential>; the credential in the query string, a cookie or the body counts for nothing. It is compared with crypto.timingSafeEqual over equal lengths (sameSecret). Otherwise 401, with WWW-Authenticate: Bearer. An agent token is not the credential.
  4. /agent/… needs a live agent token as a bearer token (isAgentToken). Otherwise 401. The control credential is not a token.

Each refusal is logged at warn as http.refused with method, path (never the query), reason (host_forbidden, origin_forbidden, credential_missing, credential_invalid, token_missing, token_invalid), api (v1, agent, other) and count, and never a secret. The logging is bounded, because every peer, containers included, reaches the daemon as 127.0.0.1: per reason and API, the first refusal after a quiet second is logged at once with count: 1; later ones in that second are counted and logged as one record when it ends; pending counts are logged as the daemon stops (RefusalLog in src/daemon/refusal-log/).

Build, run and the daemon

The owner, 2026-09-26

npm runs only at build time; the installation is a built repo checkout, or the Homebrew keg made from a release (added 2026-09-27). The daemon starts itself, announced on stderr only with --verbose, like every other progress line — runCli in src/cli/commands.ts sets progress to a no-op without it (changed 2026-09-28, the owner's answer of 2026-09-27: this said "unless --quiet is given", and before 2026-09-27 "every time"). A stale daemon is warned about, never restarted, since a restart would end running agents. The owner reaffirmed this on 2026-09-27 for a daemon that lacks a security fix too ("Keep warning only", decisions/queue.json record stale-daemon-security): the warning is the signal, and asha --stop is the user's call.

  • Build time is npm install && npm run build in the repo. The build compiles dist/, then makes dist/agent-packages/ (tools/agent-packages/build.mts, added 2026-10-03 by docs/plans/debt-paydown.md R10): package.json and package-lock.json copied into dist/.agent-packages-install/, an offline npm ci --omit=dev --ignore-scripts of the lockfile there (600 s bound; each tarball checked against its integrity), the agent packages' runtime files copied out by copyAgentPackages with the two files beside them, the install folder removed; a package missing from the npm cache fails the build, naming it (build: the npm cache does not hold an intact copy of …). Run time is every ./asha command: the asha script runs the built CLI (dist/src/cli/main.js), never npm. With no dist/ it exits 1 and names the build command; it follows symlinks, so it can be linked onto your PATH.

  • Installed with Homebrew, the same files come from a release (Deployments): the keg's libexec/ holds asha, dist/, catalogue/, images/, recipes/, package.json, package-lock.json, LICENSE, and in node_modules/ exactly the runtime files an agent image stages: both are copied by copyAgentPackages in src/daemon/images/index.ts from the build's dist/agent-packages/ (above), which ships inside dist/, so an image is staged from the lockfile's packages as published and never from a checkout's node_modules/, where a stray or edited file would be copied (corrected 2026-10-03: until debt-paydown R11 staging copied the installation's own node_modules/, D22, now paid), and bin/asha is a wrapper that puts Homebrew's node first on PATH, then Homebrew's bin (for colima, docker and llama-server), and runs libexec/asha. It may therefore value-import other src/ modules — it imports present (src/shared/assert-present.ts) and byCodeUnit (src/shared/order.ts) — but it, and every module it value-imports, MUST use only TypeScript syntax that stripping can erase: no parameter property, no enum.   • The daemon starts itself. A message (one of an --interactive session too), /watch on, --launch or --watch that finds no daemon spawns a detached asha --server (logging to logs/server.log), prints › started the asha daemon (pid N) with --verbose, and waits up to 20 s for it (startServer).

  • It leaves when nothing needs it (docs/plans/idle-shutdown.md, 2026-10-15; DaemonLifetime in src/daemon/lifetime.ts). Three variables in the daemon's environment, read and checked by asha --server before it starts (a value that is not a positive whole number, or a pid no process of this user holds, fails the start naming it):

    • ASHA_IDLE_EXIT_MS: with no agent in any phase, no launch, restart, channel stop or approved module call in progress, and no request or stream open on its socket for this long, the daemon stops itself (daemon.stop_requested with source: 'idle' and the idleMs it measured) and exits 0. Requests and streams are counted as they begin and end; the agents' work is read at each check, every 60 s or as often as the bound is long. The auto-start sets it to 1,800,000 (30 minutes) unless the environment already does (autoStartEnv in src/cli/commands.ts); an open asha --watch or portal tab keeps the daemon alive. asha --server run by you, without it, never stops for idleness — that is how to keep one.
    • ASHA_MODEL_IDLE_MS (default 900,000, 15 minutes): a model server with no call holding it for this long is stopped, model_server.unloaded_idle (model, idleMs), and the next call that needs it starts it again (Models).
    • ASHA_EXIT_WITH_PID: the daemon stops (source: 'parent_exited', pid) within 5 s of that process ending. Every daemon a test run starts carries it, set to the vitest process, with a 10-minute idle bound and a day's model bound (tests/helpers/test-daemon-env.ts).

    Every check is a timer that never keeps the process alive, armed once daemon.started is logged and cleared by any stop. Each llama-server ends with its daemon however the daemon ended, SIGKILL included: it runs under a watch that sees the daemon's pipe close (Models).

  • One daemon per home. It holds daemon.lock, an exclusive pid lock, and writes daemon.json ({pid, port, credential}, mode 0600) once listening on a port the OS chose. A dead process's lock is cleared with lock.stale_cleared, only while holding the clear-sentinel daemon.lock.clear (acquirePidLock in src/daemon/process/pid-lock.ts, since debt-paydown R19), so two takers clearing one stale lock never both hold it. When two CLIs race, the second daemon exits (LockHeld) and its CLI uses the first. A daemon.json whose daemon no longer answers is reported on stderr and treated as not running.

  • A stopping daemon says so. The stop's first step rewrites daemon.json as {pid, port, credential, stopping: true} (synchronously, so no request is served before the control API starts answering 503 {error: 'the daemon is stopping', reason: 'stopping'}), and the file is removed as the stop's last step, after daemon.lock is released — only while it still names this daemon's pid, so a new daemon's file written meanwhile stays (removeOwnDaemonFile) (markStopping, stopDaemon in src/daemon/compose.ts; debt-paydown R14). A write that fails is logged daemon.stopping_file_failed, and the file is removed at once, as before. The CLI reads either sign as stopping, when the pid is alive and is an asha daemon (its command ends /dist/src/cli/main.js --server); CLI, the daemon says what each command then does.

  • Which build is running. A daemon and its agents keep running old code after a rebuild. Each process fingerprints dist/ at start (buildFingerprint: sha256 over every .js file but those under dist/agent-packages/, which are not the daemon's code and which every staging reads afresh, first 12 hex digits); GET /v1/health and --status report build and startedAt. Every command but --stop compares builds (findDaemon) and warns on stderr, with or without --verbose (once per build in a command or an interactive session), if they differ (below); a daemon too old to report a build shows as "unknown". The control credential and the agent token

  • The control credential. 256 random bits (randomBytes(32), hex) made by startDaemon in src/daemon/compose.ts at every start, before the server is created, and written only into daemon.json ({pid, port, credential}) by writePrivateFile: a new file opened wx with mode 0600 under a unique name, then renamed over daemon.json, so neither a stale file's mode nor a half-written file is ever seen. A new ASHA_HOME is created 0700 (ensureHome in src/shared/paths.ts); an existing one keeps its mode. The CLI reads it before its first request and sends Authorization: Bearer <credential> on every one (CLI, the daemon). It never reaches a container: nothing that specifies or starts one can hold it (a guard in tests/unit/secrets-guard.test.ts), and the eval looks for it inside a running container. It dies with the daemon: the stop removes daemon.json once the lock is released (above).
  • The agent token. A random 256-bit token per agent container, ASHA_AGENT_TOKEN, made at launch (randomBytes(32) in AgentSupervisor.launch), held only in the daemon's memory, and dead with the container. The supervisor keys its records by it, so it says which agent (handle and channel) is calling. There is nothing for a user to configure.
  • Travel. The token is passed by name (docker run -e ASHA_AGENT_TOKEN, ColimaRuntime.start), so it is not in a process argument listing, though docker inspect shows it (Config.Env). The agent sends Authorization: Bearer … on every call; without a live token an /agent/ call gets 401.
  • Fails loudly. A missing ASHA_URL or ASHA_AGENT_TOKEN in a container fails at start with MissingAgentEnvironment (readAgentEnvironment in src/agent-sdk/index.ts).

Why inference runs on the host

  • No GPU in the VM. colima runs Docker Engine inside a Linux VM (Lima, on macOS Virtualization.framework) with no Metal GPU; llama.cpp on the host uses Metal directly. So models are served on the host and agents reach them only through the daemon (Models).
  • Reaching the host. Containers reach the host's loopback through host.docker.internal (ColimaRuntime.hostAddress), which colima resolves to 192.168.5.2, and the host sees every such connection as coming from 127.0.0.1; verified 2026-09-26, with colima's non-interactive start (evidence), and 2026-09-27 on colima 0.10.1 (below).
  • Only the daemon's port, and nothing else. An agent container can open a connection to one address and port: its own daemon's port on the host gateway. Every other host-loopback port — each llama-server, another home's daemon, any other local service — is refused, and so is every other destination: the internet, the LAN and the colima VM itself (docs/plans/agent-tools.md R14, 2026-09-27). No outside name resolves (debt-paydown R1, 2026-10-03; D18, now paid): every agent container is created with --dns 192.0.2.1 (AGENT_DNS_SERVER, a TEST-NET-1 address, RFC 5737) and --add-host host.docker.internal:192.168.5.2 (HOST_GATEWAY) by ColimaRuntime.start in src/daemon/container-runtime/index.ts. With --dns set, Docker's embedded resolver forwards a query from the container's own namespace, where the home's reject refuses it inside the VM (resolve4 answers ESERVFAIL); without it, it forwarded from the VM's namespace, which no rule on the bridge sees, and outside names resolved. host.docker.internal, which Docker's DNS answered before, comes from /etc/hosts. Proven in the gate from inside a real agent container — through its own resolver, and with queries sent straight to 1.1.1.1, the VM's 192.168.5.1 and its bridge gateway over UDP (no answer) and TCP port 53 (refused) — against a control on the same home network without the flags (tests/agents/egress.test.ts), and by the isolation eval. The other containers are unchanged: a module and a command plugin run on the module's --internal network, which resolves only the egress proxy's name; one-shot, holder, rollback and emptying containers run --network none; the egress proxy runs on its own network, which is not internal, and resolves outside names by design — it is the one door out, for each module's allow-listed hosts (modules). Corrected 2026-10-03 by debt-paydown's completion review (finding 6): this said plugin and egress-proxy containers run --network none. The threat covered: data leaving an agent container in DNS queries to an outside resolver. Not covered: what an agent sends through the one connection it keeps, the daemon's port (its channel, its model calls, the modules it is granted). This is an obligation of the ContainerRuntime contract, not of one adapter: ensureReady(hostPort) takes the one port containers may reach, must not resolve until every container start then runs is confined to it, and must throw if it cannot; the supervisor then fails the launch and starts nothing (ContainerIsolationFailed, wire reason container_runtime). No container gets --ip, --cap-add, --privileged or the host network.
  • How ColimaRuntime confines them. Several daemons, one per ASHA_HOME, can share the default profile with containers that are not asha's, so everything is keyed on asha's own bridge interfaces:
    • Per home, a network. Containers run on asha-<homeId> (docker run --network), a bridge whose interface is asha<homeId>, where homeId is the first 8 hex characters of the sha256 of the absolute home (HarnessPaths.homeId). It is created with --driver bridge, --opt com.docker.network.bridge.name=asha<homeId>, --opt com.docker.network.bridge.enable_icc=false, --ipv6=false and a subnet Docker allocates, which the daemon records. Before each launch it is inspected and must still have driver bridge, that bridge name, exactly the recorded subnet, EnableIPv6 false and enable_icc "false". Agents cannot reach each other (added 2026-09-27, agent-tools completion review finding 5): without enable_icc=false, traffic between two containers on one bridge never reached an iptables rule — the VM had no br_netfilter — and one agent container opened a port on another's address. With it Docker loads br_netfilter in the VM (bridge-nf-call-iptables 1, observed 2026-09-27), so bridged traffic passes FORWARD too and the home's reject answers it (ECONNREFUSED, tests/agents/egress.test.ts). The module is VM-wide; Docker's own rules keep other bridges' traffic as it was.
    • One chain. In the VM's filter table, rule 1 of DOCKER-USER (traffic the VM forwards) and rule 1 of INPUT (traffic to the VM itself) are each -i asha+ -j ASHA-AGENTS. ASHA-AGENTS holds, per home, one allow, -i asha<homeId> -d 192.168.5.2/32 -p tcp --dport <daemon port> -m comment --comment asha:<homeId> -j RETURN, and right after it one reject of everything else from its bridge, -i asha<homeId> -m comment --comment asha:<homeId> -j REJECT (icmp-port-unreachable; a connection sees ECONNREFUSED at once); below them two shared rejects for asha+ to 192.168.5.2 (tcp-reset for TCP, then icmp-port-unreachable). No rule matches an interface outside asha+, so other containers in the profile are untouched, and a home with no reject of its own (a daemon from before 2026-09-27) is unchanged by the INPUT jump. The design fails closed.
    • One colima ssh per launch, colima ssh --profile default -- sudo sh -s, bounded at 30 s, its script on standard input (installScript): under flock /run/asha-iptables.lock (so daemons of different homes never interleave), it checks that host.lima.internal in the VM's /etc/hosts is 192.168.5.2, creates the chain, the shared rejects and the two jumps only where missing, moves each jump to rule 1, and replaces this home's tagged rules with exactly its allow and then its reject in a single iptables-restore --noflush that declares no chain, so it applies entirely or not at all; then it verifies the result — both jumps first, the allow, the reject, the two in that order, the shared rejects — and exits 5 naming whatever is missing, which fails the launch. It is logged as agent.isolation_ready with jumpFixed, inputJumpFixed, homeRulesReplaced and its durationMs (the network inspection plus the call). Within a daemon these changes run one at a time.
    • Lifecycle. A VM restart drops the rules, so they are verified, and reinstalled where missing, before every launch. At start the daemon reclaims its home (reclaim, reclaimScript): if the profile is running, one colima ssh removes every rule tagged asha:<homeId>, force-removes any container still on asha-<homeId> or carrying its asha.home label (only a dead daemon of this home could have left one; removeHomeContainers) — tolerating exactly Docker's "removal … is already in progress" (a dead daemon's --rm container removing itself) and "No such container", waiting up to 20 s for such a removal to finish inside the reclaim's 30 s bound, and failing on any other answer — and removes the network, logged as isolation.reclaimed. Each docker listing the script reads (the containers by network and by label, the volumes, the networks) is assigned to a variable of its own under set -e, so a listing that fails fails the reclaim, never read as an empty one (removeHomeContainers, reclaimScript); with colima absent or stopped there is nothing to remove (isolation.reclaim_skipped). A clean stop does the same once every agent has stopped. A daemon only ever deletes rules tagged with its own id; the jump, the chain and the shared rejects stay for the others. A failure of any step fails the start, the launch or the stop with ContainerIsolationFailed, naming the rule, network or check and carrying the command's output. A command past its bound is typed as well: a root script's colima ssh (the confinement's, the reclaim's, the egress rules') past its 30 s is ContainerIsolationFailed naming the step, and a docker call of the home network's past its bound ContainerIsolationFailed naming the network; any other docker call past its bound is a ContainerRuntimeError — DockerTimedOut, naming the docker command (network create, volume rm) but never its arguments, which may hold a plugin call's, or for a plugin container's docker create naming the container; colima start or colima status past theirs is ContainerRuntimeError; and docker build past its 10 minutes ImageBuildFailed (ColimaRuntime's ssh, docker, colima and confine in src/daemon/container-runtime/index.ts).
    • External facts (run 2026-09-27; plan, question 5 (docs/plans/control-api-auth.md) and its eval): colima 0.10.1; Docker 29.2.1 in the default profile's VM (29.5.2 in a throwaway profile); iptables v1.8.10 (nf_tables), which prints the comment quoted (--comment "asha:<homeId>") and applies an iptables-restore --noflush file entirely or not at all (a -D of a missing rule left the file's -I unapplied); DOCKER-USER rules survive a Docker restart but not a VM restart; the network survives a VM restart. The eval (tests/eval/isolation.eval.test.ts) proves the confinement on the default profile with two daemons at once, against a control container on Docker's default bridge.
  • Bounded. brew install colima docker gets 15 minutes (INSTALL_TIMEOUT_MS in host-tools); the start gets 10 (START_TIMEOUT_MS in container-runtime); each colima ssh 30 s (SSH_TIMEOUT_MS), within which the lock is waited for at most 20 s. The harness uses colima's default profile and never stops it.
  • Not vLLM. vLLM (vllm-metal) was evaluated on 2026-09-26 and set aside by the owner: it is macOS-native too, and llama.cpp covers Metal and CUDA with one fewer moving part. On a PC only the container runtime and model server adapters would change: planned: pc-cuda.

Where things live

The home is ASHA_HOME, default ~/.simplyautonomous/harness (harnessPaths in src/shared/paths.ts). One that does not exist is created with mode 0700; an existing one keeps its mode.

Note

Channels, conversations, deliveries and tokens are in the daemon's memory only; a daemon restart ends them. What a persisted agent or team keeps across a restart is under state/ (below).

The memory agent's tiers live in its own container (Agent memory), and, for a recipe that persists them, are also saved under state/ (persisted memory).

Saved state is written by StateStore (src/daemon/state/store.ts): directories 0700, files 0600; a checkpoint writes gen-<n+1>/ beside the pointer (created exclusively, every file written and fsynced, the directory fsynced), then replaces current.json (write, fsync, rename) and fsyncs the identity directory, and only then deletes the previous generation, so a crash at any point leaves the previous pointer and its generation intact. A failure of the identity directory's fsync after the pointer's rename (PromotionUnsynced) keeps both generations: the pointer on disk already names the new one, so the checkpoint is reported write_failed (state.save_failed), its discard removes nothing, and the next start removes the one the pointer does not name. At start the daemon removes what a crash left — a generation the pointer does not name, a stray .*.tmp — each logged state.orphan_removed (warn); a pointer naming a generation that is missing fails the start with StateStoreCorrupt naming it, before any generation of that identity is removed (cleanupAtStart). Everything under state/ is walked without following links; a link or special file there is StateStoreCorrupt. Never in a git tree: before the first read or write in a run, and at start whenever state/ exists, insideGitTree (src/shared/paths.ts) checks for a .git directory or file at or above it; found, the start or the persisted launch is refused (StateInsideGitTree, state_inside_git_tree). With nothing persisted and no state/, the check never runs. The offline --list-state and --reset-state hold daemon.lock for the command (CLI).

Logs, the 3am query, and error events

JsonLinesLogger in src/daemon/log.ts is the daemon's one logging facade (PRINCIPLES §11): one JSON line per record in logs/daemon.jsonl, echoed to stderr; ts, level and event written last as well as first so no field overwrites them; errors serialized with name, message, stack and cause chain (serializeError); and written synchronously, so a record is on disk before a crash that follows it.

// Synchronous on purpose: a record must be on disk before a crash that

The record is one JSON line per span, written when it ends, with exactly these keys and no others: traceId, spanId, parentSpanId (null only for asha.conversation), name, kind (conversation, delivery, call, model_call or post), channel, handle, start and end (ISO-8601 UTC, milliseconds), status (ok or error) and reason (null, or one of handler_failed, agent_left, expired, unanswered, timeout, unavailable, upstream_error, bad_response, truncated, refused). For a span an agent sent, handle and channel come from its token, never from the request, and every attribute, event, link, resource attribute and scope it carried is dropped (parseOtlpTraces, receiveSpans in src/daemon/traces/index.ts).

  • The traces route (POST /agent/v1/traces, the APIs) takes OTLP/HTTP JSON with the agent's token, on the daemon's own listener; it opens no port. It refuses a whole request (400) whose body is not JSON, has no resourceSpans, or holds a span whose IDs are not lowercase hex of the right length, whose times are not decimal strings or end before they start, whose spanId repeats one earlier in the request, whose name is not delivery, chat, embed or post, whose status.code is not 0, 1 or 2, or whose error status's message is not a reason above. A span of a trace not delivered to the agent (the daemon keeps that set for the agent's lifetime) is dropped and counted.
  • The files. logs/traces-YYYY-MM-DD.jsonl, dated by the UTC date at which the daemon writes (a request's receipt, a daemon span's end). Each request's records are one synchronous append, each daemon span one, so a record is on disk before the channel event that follows it. A file never passes 64 MiB (TRACE_FILE_CAP_BYTES): an append that would is dropped whole and its spans counted.
  • Shared fairly. So that no agent can crowd out the others or the daemon (one agent filled the whole file in under a second before this; found by the completion review, 2026-09-27), agents' spans stop 16 MiB short of the cap (TRACE_DAEMON_RESERVE_BYTES: that part is the daemon's own, about 58,000 records), and each agent — keyed by channel and handle — may add at most 4 MiB a UTC day (TRACE_AGENT_DAILY_BYTES: 1,400–3,800 conversations of its spans; twelve agents at their budget fill the agents' 48 MiB). A request past its agent's budget is dropped whole, counted in its rejectedSpans, and logged at warn as traces.agent_over_budget: once with budgetBytes at the agent's first drop of the day, once with its count at the next day's first write or a clean stop. At startup and at each day's first write, files dated more than 7 days back are deleted, so at most eight (512 MiB) exist (TraceFileWriter).
  • In flight. Whether a model call is in flight is not in the files, which hold ended spans only: the supervisor holds the open asha.chat and asha.embed spans, and AgentSupervisor.modelCallsInFlight returns a read-only view of them (name, IDs, channel, handle, start; no means to end one).

The OpenTelemetry packages and their licences
