# Modules

A module adds to asha what it does not do on its own: a web search, a hosted model, a command-line tool that reaches a cloud service. Each is contributor code that may hold a secret, reach the internet and spend money, so asha runs it in its own locked-down container, lets an agent reach it only through the daemon, and holds every call that changes something outside the machine for the user's approval.

> [!SUMMARY]
> - Three kinds: a **ToolModule** (tools an agent calls), a **ModelProvider** (a hosted model a recipe names in place of a local one) and a **CommandTool**, a command plugin wrapping a program such as the AWS CLI.
> - A module is a directory with a closed manifest, `module.json`, installed with `asha --install-module` while no daemon runs; its code never runs in the daemon or an agent container.
> - A recipe grants module tools by name in its `modules` list; the agent calls them only through the daemon's module-call route.
> - Each module runs in its own container on its own internal network, reaching the internet only through the egress proxy, which allows its manifest's hosts on port 443 and nothing else.
> - A call classed `consequential` is never sent until the user approves it with `asha --approve`; asha then makes exactly that call once, audits it, and gives the agent the result as its own data.
> - A metered module stays off until the user opts in with three spending caps; an image that keeps memory is never beside a cloud-granted agent.
> - With no module installed, nothing changes: no check, network or container is added, and every model request is byte for byte as before.

## The three kinds {#kinds}

| Kind | What it is | Runs as | Reaches the agent as |
|---|---|---|---|
| `ToolModule` | plain JavaScript exporting `call(tool, args, context)` | one container per (module, channel), from the module base image | tools `<module>__<tool>` offered to the model after the selected tools |
| `ModelProvider` | plain JavaScript exporting `chat(args, context)`, and optionally `embed` and `lifecycle` | the same | the recipe's `model` or `embeddingModel`, served on the same chat and embed routes as a local model |
| `CommandTool` | a Dockerfile that installs one program from a release archive the user supplies | one fresh container per command call | each declared command, as one tool |

The contracts the module's code meets are in [`src/module-runtime/runtime.ts`](../../src/module-runtime/runtime.ts) (`handleLine`, `ModuleEntry`, `CallContext`): `context.secrets` holds only the module's own declared secrets, `context.idempotencyKey` is set on a consequential call (pass it to the vendor's idempotency mechanism where it has one), and a provider streams with `context.onDelta`. A handler answers `{ok: true, result, usage?}` or `{ok: false, reason, detail?}`, the reason from `TOOL_FAILURE_REASONS` for a tool and `MODEL_FAILURE_REASONS` for a provider; a handler that throws is answered `module_unavailable` (a provider's `unavailable`), its error logged.

## The manifest {#manifest}

`module.json` has a closed schema, parsed by `parseModuleManifest` in [`src/shared/modules.ts`](../../src/shared/modules.ts); an unknown field, a missing one, or any rule below broken fails the daemon's start, naming the module and the field.

| Field | Rule |
|---|---|
| `id` | `^[a-z][a-z0-9_]{0,31}$`, the directory's name; a tool's wire name is `<id>__<tool>` |
| `kind`, `version`, `entry` | the kind above; the version; the entry file (`Dockerfile` for a command plugin) |
| `files` | the sha256 of every file in the directory but `module.json`, never a name beginning with `.` |
| `licence` (and `dependencies`) | SPDX id, the licence's URL at that version and the date read; only `MIT`, `ISC`, `Apache-2.0`, `BSD-2-Clause`, `BSD-3-Clause`, `0BSD` are installed |
| `hosts` | every host the module may reach; a wildcard is `*.` and at least three more labels (`*.s3.us-east-1.amazonaws.com` passes, `*.amazonaws.com` does not) |
| `secrets` | the names of the secrets it needs, each set with `asha --set-secret`; never a name the docker CLI or the harness uses — `PATH`, `HOME`, `TMPDIR`, `DOCKER_*`, `DYLD_*`, `LD_*`, `NODE_*`, `*_PROXY` and the others `reservedVariableName` lists — which would change what the host runs (a command plugin's fixed environment likewise) |
| `cost` | `free`, `local`, `metered` (a tool module's `perCall` price with its source and date) or `external-unmetered` (a command plugin's alone: a tool module or provider that spends is metered); the owner's approval `approved {by, date, capUsd}` |
| `tools` | each tool's name, description (at most 512 bytes; each parameter's at most 200, with no invisible or direction-changing character), classes, `timeoutMs` (at most 60,000) and JSON Schema parameters |
| `models` | a provider's models, each pinned by the vendor's exact id (no `latest`, no inference profile, no ARN), with its card, launch date, prices, terms and retention policy, each with its URL and date read ([Models](models.md#providers)) |
| `executable`, `commands` | a command plugin's program, its archives per architecture, its signature record and fixed environment; each command's prefix, fixed options and typed arguments ([below](#plugins)) |

**Tool classes** say what a tool does, from a closed set: `untrusted-input` (it returns text from outside, such as web pages), `egress` (it sends data off the machine; every tool of a module that lists a host must carry it) and `consequential` (it changes something outside the machine; only a module that lists a host may have one). The classes drive the approval rules below.

The approved caps of every installed module may sum to at most $50 a month, the owner's approval of 2026-09-27; a start over it fails naming the total (`APPROVED_CAP_TOTAL_USD` in [`src/daemon/modules/installed.ts`](../../src/daemon/modules/installed.ts)).

## Install, upgrade, uninstall {#install}

`asha --install-module path=<dir> [archive=<file>] [--yes]` ([`src/daemon/modules/install.ts`](../../src/daemon/modules/install.ts), `installModule`) runs in the CLI only, never beside a daemon of the home: with one answering it prints `✗ a daemon is running for this home; stop it first: asha --stop` and writes nothing; otherwise it holds `daemon.lock` throughout. It downloads nothing. It checks every file's sha256 against the manifest, refuses a file not in the manifest, a symbolic link, a lockfile entry without `integrity` or with `hasInstallScript`, a dependency with no licence entry or whose `package.json` says another licence, and a licence off the allowlist; prints the summary — id, version, hosts (every wildcard), secrets, every tool with its classes and description, and the cost model, every free-text string with its control and invisible characters shown as `\u` escapes — and asks for `yes` on a terminal (off one, only `--yes` proceeds). It copies the module into a fresh `ASHA_HOME/modules/.staging-<random>/` — the manifest's bytes as read once, parsed and confirmed, and every other file hashed as copied and refused unless it is the manifest's sha256, so what is installed is what was checked — and promotes it by one `rename`; an upgrade renames the installed version aside first and deletes it last, and the next install repairs what a killed one left, logged. A tool module's or provider's image is built at install from the module base ([images](#images)).

`asha --uninstall-module id=<id>` removes the module's directory and its secrets, under the same lock. Both apply identically to a module from this repository (`modules/<id>`) and to one from anywhere else: a module is a directory anyone may publish.

The daemon reads only manifests at its start, and only for directory names not beginning with `.`; a module's code runs only when an agent granted it comes online. A `.replaced-<id>-*` with no `<id>/` beside it is logged at error at start, `module.upgrade_interrupted`, naming the repair.

## The sandbox {#sandbox}

![An agent reaches a module only through the daemon: the grant and the arguments checked, a consequential call held for approval, then one request line to the module's own container, or a one-shot container for a command. The module reaches the internet only through the egress proxy, whose bridge is fenced by iptables rejects.](modules-flow.svg)

- **Its own container, never the daemon.** The daemon never imports or evaluates module code. A tool module or provider runs in one container per (module, channel), started when the channel's first granting agent comes online and stopped when its last leaves ([`ModuleHost`](../../src/daemon/modules/host.ts) `acquire`, `release`), so no module state passes between channels. Each container runs with `--cap-drop ALL`, `--security-opt no-new-privileges`, `--pids-limit 256` and `--cpus 1` (`MODULE_LIMITS` in [`src/daemon/container-runtime/index.ts`](../../src/daemon/container-runtime/index.ts)), and `--memory 512m` (1 GiB for a plugin call) and, for a module or the proxy, `--read-only` with a 64 MiB `/tmp`, added where each is started (`runAttached`, `pluginContainer`). A container's variables are passed by name, their values in the docker CLI's own environment, and a name the CLI or the harness uses is refused there too (`containerEnvArgs`). A plugin call's writable layer has no size bound Docker can set on colima's storage: its read set and its copy-back are bounded, but **a command may still fill the VM's disk with files it does not return**.
- **The framing.** The daemon writes one JSON request per line, `{id, tool, arguments, idempotencyKey?}`, and reads exactly one answer per request, matched by id; a provider's `{id, delta}` lines come first. A line is at most 1 MiB. A module that exits, closes stdout, writes a line that is not a valid answer, or answers with a reason outside its kind's set fails every call in flight `module_unavailable` (a consequential one `unknown_outcome`); the next call starts a new container, at most 3 times in 10 minutes per (module, channel), after which its calls fail until its agents are launched again.
- **Bounds.** A tool call ends `timeout` at its `timeoutMs` (`unknown_outcome` when consequential); a provider's at 55 s to its first chunk and 22 s between chunks. A recipe granting a tool must allow a turn that uses it: `timeoutMs` + 125,000 ms (two model calls at their 60 s bound and the SDK's 5 s margin) must fit in its `messageTimeoutMs`, or the launch is refused naming both values.
- **Its own network.** Each (module, channel) gets an internal network (`docker network create --internal`), its bridge named `asham` + 10 hex of sha256(home, module, channel) (`bridgeOf` in [`ModuleHost`](../../src/daemon/modules/host.ts)), whose one other member is the egress proxy, so a module resolves no outside name (Docker Engine 26.0.0 and later; the module host refuses an older engine, naming its version, before the first module network of a run, and a launch granting no module never checks).
- **The egress proxy** ([`src/egress-proxy/proxy.ts`](../../src/egress-proxy/proxy.ts), `EgressProxy`) is the only way out. The module base image sets `HTTPS_PROXY` to it and `NODE_USE_ENV_PROXY=1`, so `fetch` sends every request as a `CONNECT`. It allows only port 443 of a host in that module's manifest, listening once on each module network so one module's list never applies to another's connection; reads the TLS ClientHello and refuses unless its server name — byte for byte, letters, digits, dots and hyphens only — equals the `CONNECT` host; resolves the host once, IPv4 only, and dials only a public unicast address — never 0.0.0.0/8, 10/8, 100.64/10, 127/8, 169.254/16, 172.16/12, 192.0.0/24, 192.0.2/24, 192.168/16 (colima's 192.168.5.0/24 and the host among them), 198.18/15, 198.51.100/24, 203.0.113/24, 224/4 or 240/4 — so a redirect to another host is a new `CONNECT` and refused. It bounds each connection at 10 s to connect and 60 s of silence. Its entry point reads no environment variable or argument; its first line on stdout, `{"op":"ready"}`, says its container exists and it reads its orders, and the module host connects no module network to it before that line (within 10 s), since `docker run` creates the container a moment after it is spawned. A setup that fails part way removes the container and network it made. If it exits, the next call removes its container and network and sets it up again. **Stated limit:** the server-name check stops a name mismatch at the TLS layer only; on a shared CDN, a request inside the TLS session can still name another site in its `Host` header (domain fronting), which the proxy cannot see. A command plugin's container is given the same `HTTPS_PROXY` (and `HTTP_PROXY`) on every create.
- **Fenced in the VM.** The proxy's outbound side is its own bridge, `ashae<homeId>`, from which iptables rules (tagged `asha:<homeId>`, in `DOCKER-USER` and `INPUT`) reject every private range, colima's network and the host gateway; and every module bridge (`asham+`) is refused any address of the VM itself — its gateway address on that bridge, the VM's sshd, any port the VM listens on — by one shared rule, `-i asham+ -m addrtype --dst-type LOCAL -j REJECT` (`MODULE_LOCAL_REJECT`), which a reclaim never removes since another home's modules may run, while a module's traffic to the proxy on its own bridge, to no local address, passes. All of them are verified before every module container starts, its restarts included, and before every plugin call, which fails when one is missing. The rule is IPv4's: a module network is created `--ipv6=false`, and its containers' interface carries no IPv6 address, not even link-local (`disable_ipv6` is 1; the colima suite checks both), so the VM bridge's own link-local address is not reachable from a module; an engine that gave such a network IPv6 would need an `ip6tables` rule this page does not claim. *Corrected 2026-10-02:* this page said the gateway was not yet proven closed (D53); the colima sandbox suite's first run found it open — a module connected to the VM's sshd at its network's gateway — and the bridge names and the rule above close it (the same suite, `ECONNREFUSED`).
- **Labelled for the reclaim.** Every module, proxy and plugin container and every module network carries `asha.home=<homeId>`; the daemon's stop removes them, and the networks, after the containers (`networks=` in the reclaim's report), each kind in one `docker` call naming them all. With 16 channels' module containers and networks the reclaim takes about 2.2–2.6 s more, nearly all Docker removing networks and the proxy's endpoints one at a time (probes P7 and P7b, in the probe records (`evals/probes/extension-modules-2026-10-01/README.md`)); the model servers stop beside it, so the stop stays inside the CLI's 90 s.
- **Images readable by their user.** A module image is built from the installed directory staged with every file 0644 and every folder 0755 (the installer keeps its own copy 0600): the image's `node` user must read `/module` (*added 2026-10-02: every module installed with `--install-module` failed `EACCES` until then, found by the first run on colima*).

## Secrets {#secrets}

`asha --set-secret module=<id> name=<NAME>` reads the value from standard input only — never an argument or an environment variable, which a process listing or shell history would show — refuses at a terminal, where the value would show as typed, writes the store file itself (never through the daemon), and prints only the name and the value's length. The store ([`FileSecretStore`](../../src/daemon/secrets/index.ts) behind `SecretStore`) is one file per module, `ASHA_HOME/secrets/<module>.json`, mode 0600 in a 0700 directory, written by `writePrivateFile` under `secrets.lock`; it refuses when `ASHA_HOME` is inside a git working tree. A module container receives only its own declared secrets, in that container's environment alone — never another module's, an agent token, the control credential or the model servers' key — and a granted module whose secret is not set fails the launch, naming the secret and the command. Every line a module, the proxy or a plugin writes, and every answer a module gives — its result, a provider's deltas, a refusal's detail — is redacted of the module's secret values, a fragment at a line's end or start included (the halves of a value split across two lines), before it is logged or reaches a model. A module's stderr line is kept to 16,384 characters, the rest counted and dropped.

**Known exposures of the file store** (the planning agent's decision of 2026-09-27, question 3): any process running as the same macOS user can read the file, as it can `daemon.json` and `model-server.key` today; and Time Machine copies it into backups unless `ASHA_HOME/secrets` is excluded. A macOS Keychain cannot serve a daemon started by launchd before anyone logs in, so a Keychain adapter is left for installs that run only in a login session.

## Approvals {#approvals}

A call of a tool classed `consequential` never reaches the module from the agent. The flow ([`AgentSupervisor`](../../src/daemon/agents/index.ts) `requestApproval`, `approve`; [`Approvals`](../../src/daemon/modules/approvals.ts)):

1. **The request.** The module-call route answers `{ok: false, reason: 'approval_required', detail: 'approval <id>'}` (the model sees `{"error": "approval_required"}`) and records a pending request — the agent, channel, user, module, tool, the arguments in their RFC 8785 form, and the sha256 of the RFC 8785 form of `{agent, conversation, module, tool, arguments}` — in the daemon's memory only. The user sees on the conversation, on stderr, `⚠ <agent> asks to call <module>/<tool> (arguments sha256 <12 hex>); see and approve with: asha --approve id=<id>`; the notice holds no arguments. A request expires after 10 minutes; at most 64 are pending, a call past that being refused with its own notice.
2. **The approval.** `asha --approve id=<id>` reads the request, prints the agent, channel, conversation, `<module>/<tool>`, the arguments and the sha256 it computes itself from what it printed — every invisible or direction-changing character shown as a `\u` escape — and approves only on the exact answer `yes` at a terminal, or `--yes` off one. A sha256 that differs from the daemon's is refused, and so are arguments that are not their own RFC 8785 string (a duplicate key, a space), which could show one thing and hash another. No agent route can read, list or approve a request: approval needs the control credential.
3. **asha makes the call.** The approval takes the request at once, so two approvals of one id make one call. asha then makes exactly the approved call, once, with the arguments the user saw: under the meter's reservation, with an idempotency key, audited before it is sent and with its outcome, never retried; and for a command plugin with every path check made again now. No model is asked anything in between. Any failure after the request was sent ends `unknown_outcome`, since the call may have taken effect.
4. **The result, to the agent, as asha's data.** asha starts a new conversation on the request's channel, for the request's user, whose one message is from `asha`, kind `internal`, to the agent that asked, carrying `approved: {approval, module, tool, arguments, outcome}`. The agent's turn is framed from that field alone ([Channels and agents](channel.md#approved)): what was done and how it ended, that it must not be made again, and the data, named as the tool's and marked as data, never instructions. That turn offers the channel tools alone, and `decide()` runs no own or granted tool for it whatever its caller passes, so the call is never made again from it. `--approve` prints `✓ approval <id>: asha made the call <module>/<tool>: ok` with the result, or the `✗` line naming the failure, and then the agent's reply.

**A consulted agent.** An agent consulted by another may call its own granted tools in its call turn, so a consequential call can be held while the agent that consulted it waits. The approval's result goes to the consulted agent alone, in a new conversation; the agent that consulted it gets the consulted agent's answer to the original question — saying the call is pending — and nothing after.

**The single-person condition.** An approval proves only that a process of the local OS user issued it — whoever can read the control credential in `daemon.json` — not which person: user identity is self-asserted (debt D2). So a consequential module is for a machine that one person uses; the owner accepted that on 2026-09-27 (extension-modules question 2, record `approvals-without-user-auth`).

**Stated limit: an agent's words about a consequential action are not the record.** The record is the outcome line and result `asha --approve` prints, with its escapes, and the audit; an agent may misreport them. Under the approved call's frame since 2026-10-03 (`docs/plans/debt-paydown.md` R7: the result fenced between `BEGIN TOOL DATA` and `END TOOL DATA`, the instruction after it; [the frame](channel.md#approved)), the pinned model given a result holding an injected instruction — another transfer, a false failure with a resend request, text that tries to close the fence — reports the transaction and relays none of it, and the routing gate checks each of those cases 3/3. **It still relays a link a result asks the user to visit** (0/3 under every frame tried, probe P7b (ii); debt D51, narrowed to that): the user must not act on a link or request an agent passes on from a tool's result. *Corrected 2026-10-03: this said the model relayed an injected instruction word for word, as it did under the frame before R7.* D51 is to be paid, or the module's use refused, before any module's first live use (none is live: D52, D54).

**After untrusted input, sending files is consequential** (R15, the planning agent's default). In a recipe granting any tool classed `untrusted-input`, a command plugin's call that sends local file content off the machine — a `read` path argument on a command classed `egress` — is held for approval like a consequential one. In a recipe granting no such tool it runs without approval. **Stated limit:** asha cannot see text the model copies into an argument itself, so a recipe that selects the file tools and grants an `untrusted-input` tool and an `egress` tool together can leak file text through arguments — a search query holding words read from a file; grant those three together only where that is acceptable.

**Tool poisoning** (R10 (b)). A module's tool and parameter descriptions are text the model reads as instructions about the tool, so a hostile module could write instructions there. They are bounded (512 and 200 bytes), refused when they hold an invisible or direction-changing character, and printed in full in the install summary for the user to read before `yes`; a description is never changed after install without a new install and summary. What a module returns is cut to 8,192 bytes of JSON and handed to the model as the tool's result — which bounds it but cannot stop a model from following text in it.

## The audit {#audit}

`ASHA_HOME/audit/consequential.jsonl` ([`AuditLog`](../../src/daemon/modules/audit.ts)) gets one line before each consequential call is sent and one with its outcome: exactly `time, agent, conversation, module, tool, argumentsSha256, approval, idempotencyKey, outcome`, never an argument, a result or a secret. The file is only ever opened to append, by the daemon alone. At the daemon's stop, an approved call in flight ends with its container in the reclaim and is audited `unknown_outcome` unless its answer came first; the stop waits for it at most 1 s after the reclaim (`APPROVED_SETTLE_MS`).

## Cost {#cost}

- **The owner's approval** is recorded in each metered or external-unmetered manifest, `cost.approved {by, date, capUsd}`, with the estimate on the module's page; the opt-in live check refuses a module without it before anything reaches the network.
- **The meter** ([`Meter`](../../src/daemon/modules/meter.ts)): a metered module stays disabled until `asha --enable-module id=<id> conversation=<usd> day=<usd> month=<usd>` — all three, each at most the approved `capUsd`; a launch granting it before then is refused. Before each call its worst case is reserved, one reservation at a time, and refused `budget_exceeded` before any vendor call when a cap would pass; after it, settled to the vendor's reported usage, or charged in full — logged — when the call reported none or ended `timeout` or `unknown_outcome`. Days and months are UTC. `ASHA_HOME/metering.json` holds exactly `{modules: {<id>: {caps, day: {date, usd}, month: {month, usd}}}}`; each conversation's spend lives in the daemon's memory only. A file that does not parse refuses every metered launch and call (`budget_meter_unavailable`), logged, and is never reset.
- **Limits at the vendor** back the meter up, since it sees only this home's spend: an AWS Budget whose action denies the module's IAM user at its cap; at Tavily none, by the owner's choice of 2026-10-12, so the meter alone bounds asha's searches. Each module's page records the limit set, how and when, or that none is.
- **A settle past a cap** — a vendor that reported more usage than was reserved — is charged as reported and logged `budget.overrun` (warn: module, cap, limit, spent, reserved, charged).
- **The live check** (`npm run live:modules`, outside the gate) calls the vendor directly through the module host, not through the meter: one call per model or tool, at most 64 output tokens, run by hand with the owner's key (debt D54). It is green only on a pass: every call ok, and a provider's forced tool call and usage both returned (`livePassed`).
- `asha --status` lists, per agent, the cloud modules and hosted models it may send data to (`cloud=`), and per enabled metered module `<module> spend <day>/<cap> today, <month>/<cap> this month (UTC), USD`.

## What leaves the machine, and memory {#memory}

An agent's content goes only to the vendors of cloud modules its own recipe grants, and to its hosted model if its recipe names one. A recipe is **cloud-granted** when it grants a module that lists a host, or names a provider's model as its `model` or `embeddingModel` (`isCloudGrantedRecipe` in [`src/daemon/modules/launch.ts`](../../src/daemon/modules/launch.ts)). **Memory never leaves the machine:** a launch is refused (`module_refused`) when an image that keeps memory (`"keepsMemory": true` in its `image.json`) is cloud-granted, or when the recipe reaches a named root another recipe of the other kind reaches; and an agent is never brought online beside one of the other kind on a channel, nor a cloud-granted agent onto a channel a memory agent has been on in this daemon run (`memory_egress_forbidden`, naming both). The `user` field of each message — by default the login name, converted to fit the user-ID rule — reaches cloud-granted agents unchanged, as it reaches every agent, and so can reach their vendors (the owner's answer, `user-to-cloud`, 2026-09-27).

## Command plugins {#plugins}

A `CommandTool` wraps one program. Its directory holds a Dockerfile — `ARG ASHA_PLUGIN_BASE`, `FROM ${ASHA_PLUGIN_BASE}` (the digest-pinned glibc base `node:22-bookworm-slim@sha256:d415caac…`, the one base allowed besides the module base), copying `${ASHA_ARCHIVE}`, ending `USER 1000:1000`, and using only `ARG`, `FROM`, `COPY`, `RUN`, `ENV`, `WORKDIR`, `USER` and `LABEL`, with no parser directive (`# syntax=`, `# escape=`), no `--from` and no `RUN --mount`, so a build reads no other image — and **no release file of the program**: this repository redistributes no third-party program. The manifest pins each architecture's release archive by URL, sha256 and file name; the user downloads it and names it at install, `archive=<file>`. The installer reads the VM's architecture, opens the file without following a link, refuses anything but a regular file and anything over 1 GiB before reading it, copies it from that one descriptor (refusing one that grew), checks the copy's sha256, writes `.asha-install.json` with the architecture, and builds the image with `--network=none`. Before every later build the architecture and the archive's sha256 are checked again, so a changed VM or file is refused, naming both values.

**A copied file is root's, mode 0600**: the image is built from the installed directory as the installer wrote it, so a Dockerfile reads what it copies before its `USER 1000:1000`, never after (D55).

**Only the program's own licence is checked** (the owner's answer, `plugin-bundled-licences`): components bundled in its release are not assessed. The AWS CLI's are listed on [its page](modules-aws-cli.md).

A call goes through five layers, each holding on its own ([`PluginRunner`](../../src/daemon/modules/plugins.ts)):

1. **The harness builds the command** ([`buildArguments`](../../src/daemon/modules/arguments.ts)): typed values (`enum`, `integer`, `string` and `remote` with a pattern, `path` with a mode) in the order and with the options the manifest declares, as an array with no shell. A value beginning with `-`, and a string beginning with `file://`, `fileb://` or `@`, is refused; so is any option the manifest does not declare.
2. **Paths stay inside the allowed roots** ([`resolvePluginPath`](../../src/daemon/modules/paths.ts)): the channel's file space, and each folder the recipe or its team names in `roots` with a mode. A root is refused at launch when it is `/`, is or contains the home folder, is, contains or lies inside `ASHA_HOME`, lies under `~/Library`, or has a deny-listed component. Each path is normalised; every component of a root's path is `lstat`ed and a link anywhere, or a hard-linked file, refused; the copy is made through an `O_NOFOLLOW` descriptor whose identity is the file checked. The [credential deny list](../../src/shared/credentials.ts) is applied case-folded, and a file holding any value of the secret store is refused, naming the file and never the value. A write is refused into a `.git` folder — by the path the command sees and by a root's host path, so a read-write root at `<repo>/.git` is refused — a shell start-up or login file (`.profile`, `.bashrc`, `.bash_login`, `.zshrc`, `.zlogin` and the like) or `Library/LaunchAgents`, and a file the command put in place of a root folder itself is refused. A path argument is given to the command as it was checked, its `..` removed. A file the host refuses to read — macOS's protection of `~/Documents`, `~/Desktop` and `~/Downloads` for a daemon launchd started, say — ends the call `path_refused`, naming the path and the error.
3. **Only copies exist** (R30): the command runs in a fresh container where no host path is mounted. Its read set — at most 1 GiB and 10,000 files, else `input_too_large` before any container — is streamed in as one tar owned 1000:1000; each write path is copied out after it exits, read by the tar reader's rules (no link, hard link or special file), and written back into a root only once the whole tar has been read within 1 GiB and 10,000 entries (`output_too_large` otherwise, nothing renamed in), or into the channel space within its bounds, no more than a space can hold (1,000 entries, 256,000,000 bytes) staged on the host on the way (`space_full` past it). The container is removed on every path. The whole call, copies included, is bounded by the command's `timeoutMs`.
4. **Credentials live for one command** (R33): the plugin's secrets are set on that call's container alone, with the program's own credential files disabled in its manifest (for the AWS CLI `AWS_CONFIG_FILE` and `AWS_SHARED_CREDENTIALS_FILE` are `/dev/null`); stdout and stderr are captured up to 256 KiB each, redacted, and cut so the result's JSON is at most 8,192 bytes. The result is `{exit_code, stdout, stderr}` whatever the exit code.
5. **The network is the plugin's**: the call's container is on the (plugin, channel) network, reaching only the proxy and the hosts the manifest lists.

A launch granting a command plugin whose manifest lacks the owner's approval of its cost is refused. No recipe in this repository grants the reference AWS CLI plugin until its page records the proxy's evidence ([aws_cli](modules-aws-cli.md#proxy-evidence)) — a gate test ([`tests/unit/network-sites.test.ts`](../../tests/unit/network-sites.test.ts)), not a launch refusal: a recipe outside the repository can grant it.

## Images {#images}

The harness's own images live in [`harness-images/`](../../harness-images/): the **module base** (`node:22-alpine@sha256:c610fcdf…`, the module runtime, `NODE_USE_ENV_PROXY=1` and `HTTPS_PROXY=http://asha-egress:3128`), the **egress proxy**, and the **plugin base**. Each is built from the tree by digest, as agent images are, and is never an agent image (`Definitions.image` refuses their names). A module's image is the module base with its installed directory copied in, built with `--network=none`. Old versions of these images are removed by the [image prune](recipes.md#prune) at each daemon start, as agent images' are (`ASHA_REPOSITORY` in [`src/daemon/container-runtime/index.ts`](../../src/daemon/container-runtime/index.ts) matches `asha-harness-*`, `asha-module-*` and `asha-plugin-*` beside `asha-image-*`), and each missing tag is built under [its tag's VM lock](recipes.md#build-lock), as for agent images.

## What is logged {#logs}

Every record goes through the daemon's facade to `logs/daemon.jsonl` ([Logs](index.md#logs)): `module.call` (agent, module, tool, duration, outcome) and `module.failed` — an agent's call carries agent, module, tool and reason; a container's own failure, logged by the module host, carries module, channel, reason and, for a call in flight, tool, but no agent, since a container serves every granting agent of its channel; the stop's abandoned approved call carries agent, channel, module, tool and approval — `plugin.call` and `plugin.failed` (agent, plugin, command, the arguments' sha256, the paths copied in and back, exit code, duration, outcome), `egress.connection`, `egress.refused` (module, host, rule) and `egress.handle_failed` (module, host and the error: a failure inside one connection, its client closed), `budget.exceeded`, `budget.overrun` and `budget.meter_failed`, `module.approval_requested`, `module.approved` and `module.approval_undelivered` (with the request's sha256), and `module.failed` with reason `abandoned` for a call whose agent left. No line the harness writes about a request, an approval, a call or its result holds the arguments or the result. Two kinds of line are outside that rule: what a module, the proxy or a plugin prints on stderr, re-logged as `module.stderr` or `module.record` with its secrets redacted, which is the module's to keep clean; and a command plugin's path arguments, logged as the paths they are.

A daemon started from older code keeps serving plugin commands without newer guardrail fixes until `asha --stop` (the owner's warn-only answer, `stale-daemon-security`); each command warns when the daemon's build differs.

## With modules unused {#unused}

With no `ASHA_HOME/modules/`, and for every launch of a recipe with no `modules`, no `roots` and no provider model, the daemon makes exactly the calls it made before this plan: no Docker version check, no egress rule, no network, no module container; the reclaim's script also lists the home's labelled networks and finds none. Every model request is byte for byte as before, and the welcome's `modules` is `[]` — proven against a recording taken at the plan's base commit ([`tests/integration/modules-unused.test.ts`](../../tests/integration/modules-unused.test.ts)).
